Administración y configuración avanzada de Apache

Configuración del servidor web Apache, módulos, VirtualHost, autenticación, HTTPS y comprobación de funcionamiento mediante curl.

1. Administración y configuración de Apache

1.1. Instalación y funcionamiento del servicio

Apache HTTP Server es un servidor web que permite publicar páginas y aplicaciones web mediante los protocolos HTTP y HTTPS. En Debian, su instalación y administración se realizan principalmente desde la terminal.

Para instalar Apache:

apt update
apt install apache2

Una vez instalado, podemos administrar el servicio mediante systemd:

# Iniciar Apache
systemctl start apache2

# Detener Apache
systemctl stop apache2

# Reiniciar Apache
systemctl restart apache2

# Recargar la configuración sin detener el servicio
systemctl reload apache2

# Consultar el estado
systemctl status apache2

# Activar el inicio automático
systemctl enable apache2
Ejemplo 1

Comprobar que Apache está funcionando

Después de instalar Apache, podemos comprobar su funcionamiento abriendo un navegador y accediendo a: 

http://localhost/

Si Apache está funcionando correctamente, aparecerá la página de bienvenida del servidor web.

También podemos comprobarlo desde la terminal:

systemctl status apache2
Prueba desde terminal con curl

Comprobar que Apache responde

Podemos comprobar que el servidor Apache está funcionando realizando una petición HTTP desde la propia máquina Debian. 

curl -I http://localhost/

La opción -I solicita únicamente las cabeceras HTTP de la respuesta.

Para obtener las cabeceras y el contenido HTML:

curl -i http://localhost/

Si Apache funciona correctamente, recibiremos una respuesta similar a: 

HTTP/1.1 200 OK
Date: ...
Server: Apache/2.4...
Content-Type: text/html

El código 200 OK indica que la petición se ha procesado correctamente.

1.2. Archivos y directorios de configuración

En Debian, Apache utiliza una estructura de directorios que permite organizar la configuración del servidor, los sitios web, los módulos y los registros.

Ruta Descripción
/etc/apache2/ Directorio principal de configuración.
/etc/apache2/apache2.conf Archivo principal de configuración.
/etc/apache2/ports.conf Define los puertos de escucha.
/etc/apache2/sites-available/ Configuraciones de sitios virtuales disponibles.
/etc/apache2/sites-enabled/ Enlaces a los sitios virtuales habilitados.
/etc/apache2/mods-available/ Módulos disponibles.
/etc/apache2/mods-enabled/ Módulos habilitados.
/var/www/html/ Directorio web predeterminado.
/var/log/apache2/ Registros de actividad y errores.

1.3. Directivas de configuración

Apache utiliza directivas para definir el comportamiento del servidor. Estas directivas se escriben en archivos de configuración y pueden agruparse dentro de bloques específicos.

Algunas de las directivas más importantes son:

  • ServerName: nombre del servidor.
  • Listen: puerto en el que escucha Apache.
  • DocumentRoot: directorio que contiene los archivos web.
  • DirectoryIndex: archivo que se carga por defecto.
  • ErrorLog: archivo donde se registran los errores.
  • CustomLog: archivo donde se registran las peticiones.
  • AllowOverride: permite o impide el uso de archivos `.htaccess`.
Ejemplo 2

Configuración básica de un directorio web

Podemos configurar el directorio principal de una aplicación web mediante un bloque Directory. 

<Directory /var/www/html>
    Options -Indexes
    AllowOverride None
    Require all granted
</Directory>

En este ejemplo se desactiva el listado automático de directorios, se impide el uso de archivos .htaccess y se permite el acceso a los recursos.

1.4. Permisos y registros

El usuario que ejecuta Apache necesita permisos para leer los archivos publicados. En Debian, el usuario habitual es www-data. 

# Consultar los permisos
ls -l /var/www/html

# Asignar propietario y grupo
chown -R www-data:www-data /var/www/html

# Establecer permisos de lectura y ejecución
chmod -R 755 /var/www/html

Los registros principales son:

/var/log/apache2/access.log
/var/log/apache2/error.log

Para consultar los últimos errores:

tail -f /var/log/apache2/error.log

2. Módulos y funcionalidades de Apache

2.1. Sistema de módulos

Apache utiliza módulos para ampliar sus funcionalidades. Estos módulos permiten incorporar características como autenticación, compresión, reescritura de URL, cifrado HTTPS y gestión de cabeceras HTTP.

En Debian, los módulos se administran mediante los comandos a2enmod y a2dismod. 

# Habilitar un módulo
a2enmod nombre_modulo

# Deshabilitar un módulo
a2dismod nombre_modulo

# Consultar los módulos cargados
apache2ctl -M

# Comprobar la configuración
apache2ctl configtest
Ejemplo 1

Habilitar módulos habituales

Habilitamos los módulos de reescritura y gestión de cabeceras:

a2enmod rewrite
a2enmod headers

systemctl reload apache2

Podemos comprobar que están cargados mediante: 

apache2ctl -M

2.2. Reescritura de URL con mod_rewrite

El módulo mod_rewrite permite modificar las URL solicitadas por los clientes. Se utiliza para crear direcciones más sencillas, redirigir páginas antiguas o establecer reglas de acceso.

Para habilitarlo:

a2enmod rewrite
systemctl reload apache2

Las reglas se definen mediante las directivas RewriteEngine, RewriteRule y RewriteCond.

Ejemplo 2

Redirigir una URL antigua hacia una nueva

Supongamos que queremos que las peticiones a /antigua se redirijan a /nueva.

Dentro del VirtualHost podemos escribir:

RewriteEngine On
RewriteRule ^/antigua$ /nueva [R=301,L]

La respuesta 301 indica que la redirección es permanente. La opción L indica que no se deben procesar más reglas.

Prueba desde terminal con curl

Comprobar una redirección

Podemos comprobar si Apache está realizando correctamente una redirección utilizando: 

curl -I http://localhost/antigua

Si la regla está configurada como una redirección permanente, deberíamos recibir una respuesta similar a: 

HTTP/1.1 301 Moved Permanently
Location: http://localhost/nueva

Para seguir automáticamente la redirección y consultar la respuesta final: 

curl -L -i http://localhost/antigua

2.3. Gestión de cabeceras HTTP con mod_headers

Las cabeceras HTTP permiten transmitir información adicional entre el cliente y el servidor. Apache puede modificarlas mediante el módulo mod_headers.

Ejemplo 3

Añadir cabeceras de seguridad

Podemos añadir determinadas cabeceras HTTP a las respuestas del servidor: 

Header always set X-Content-Type-Options "nosniff"
Header always set X-Frame-Options "SAMEORIGIN"
Header always set Referrer-Policy "strict-origin-when-cross-origin"

Estas cabeceras permiten establecer determinadas políticas de seguridad relacionadas con el contenido, la carga de páginas dentro de marcos y el envío de información de referencia.

3. Configuración de VirtualHost

3.1. Concepto de alojamiento virtual

Los VirtualHost permiten alojar varios sitios web en un mismo servidor Apache. Cada sitio puede tener un nombre de dominio, un directorio de publicación y unos registros independientes.

Apache utiliza principalmente la cabecera HTTP Host para determinar qué sitio debe responder a una petición.

En Debian, las configuraciones de los sitios se guardan en: 

/etc/apache2/sites-available/

Los sitios habilitados se encuentran en: 

/etc/apache2/sites-enabled/

3.2. Crear un VirtualHost

Para crear un sitio web debemos preparar su directorio, crear su archivo de configuración y habilitarlo.

Ejemplo 1

Crear el sitio empresa.local

Primero creamos el directorio y una página de prueba:

mkdir -p /var/www/empresa

echo "<h1>Web de Empresa</h1>" > /var/www/empresa/index.html

Creamos el archivo /etc/apache2/sites-available/empresa.conf: 

<VirtualHost *:80>
    ServerName empresa.local

    DocumentRoot /var/www/empresa

    <Directory /var/www/empresa>
        Options -Indexes
        AllowOverride None
        Require all granted
    </Directory>

    ErrorLog ${APACHE_LOG_DIR}/empresa_error.log
    CustomLog ${APACHE_LOG_DIR}/empresa_access.log combined
</VirtualHost>

Habilitamos el sitio y recargamos Apache:

a2ensite empresa.conf
apache2ctl configtest
systemctl reload apache2

3.3. Configurar varios sitios web

Podemos crear tantos VirtualHost como necesitemos, siempre que dispongamos de los recursos necesarios.

Ejemplo 2

Crear un segundo sitio: tienda.local

Creamos su directorio y página principal:

mkdir -p /var/www/tienda

echo "<h1>Web de Tienda</h1>" > /var/www/tienda/index.html

Creamos /etc/apache2/sites-available/tienda.conf: 

<VirtualHost *:80>
    ServerName tienda.local

    DocumentRoot /var/www/tienda

    <Directory /var/www/tienda>
        Options -Indexes
        AllowOverride None
        Require all granted
    </Directory>

    ErrorLog ${APACHE_LOG_DIR}/tienda_error.log
    CustomLog ${APACHE_LOG_DIR}/tienda_access.log combined
</VirtualHost>

Habilitamos el nuevo sitio:

a2ensite tienda.conf
apache2ctl configtest
systemctl reload apache2

3.4. Resolución de nombres

Para acceder a los sitios utilizando sus nombres de dominio en una red local, debemos configurar la resolución de nombres.

En una máquina Linux podemos modificar el archivo: 

/etc/hosts

Por ejemplo:

127.0.0.1 empresa.local
127.0.0.1 tienda.local

Si queremos acceder desde la máquina física, tendremos que configurar los nombres en el archivo hosts de esa máquina utilizando la IP de la máquina virtual Debian. Si utilizamos VirtualBox con NAT, también podemos recurrir al reenvío de puertos.

Prueba desde terminal con curl

Probar un VirtualHost sin modificar el DNS

Podemos enviar una petición indicando manualmente la cabecera HTTP Host. Esto permite probar un VirtualHost aunque todavía no hayamos configurado su nombre en el archivo /etc/hosts. 

curl -i -H "Host: empresa.local" http://localhost/

Para probar el segundo sitio virtual:

curl -i -H "Host: tienda.local" http://localhost/

Apache seleccionará el VirtualHost correspondiente según el valor de la cabecera Host. En la respuesta podremos comprobar qué página ha servido.

4. Autenticación y control de acceso

4.1. Autenticación HTTP

Apache permite proteger determinados directorios mediante autenticación HTTP. De esta forma, los usuarios deben proporcionar unas credenciales válidas antes de acceder a los recursos protegidos.

Uno de los mecanismos más sencillos es la autenticación básica (Basic Authentication).

Este sistema transmite las credenciales codificadas en Base64, pero no cifradas. Por tanto, debe utilizarse junto con HTTPS para evitar que las credenciales puedan ser interceptadas.

4.2. Crear usuarios y contraseñas

Apache utiliza la herramienta htpasswd para gestionar los usuarios y sus contraseñas.

Instalamos la herramienta si no está disponible:

apt install apache2-utils

Creamos un archivo de usuarios:

htpasswd -c /etc/apache2/.htpasswd alumno

La opción -c crea el archivo. Para añadir nuevos usuarios no debemos volver a utilizarla: 

htpasswd /etc/apache2/.htpasswd profesor

4.3. Proteger un directorio

Ejemplo 1

Proteger el directorio privado

Creamos un directorio privado:

mkdir -p /var/www/empresa/privado

echo "<h1>Zona privada</h1>" > /var/www/empresa/privado/index.html

Añadimos las siguientes directivas dentro del VirtualHost o en la configuración correspondiente para proteger el directorio privado mediante autenticación.

Importante

En el directorio privado, la directiva Require valid-user sustituye a Require all granted.

No debemos mantener ambas directivas como requisitos independientes, ya que cambiaría el comportamiento de autorización y podría permitir el acceso sin autenticación. 

<Directory /var/www/empresa/privado>
    AuthType Basic
    AuthName "Zona privada"
    AuthBasicProvider file
    AuthUserFile /etc/apache2/.htpasswd
    Require valid-user
</Directory>

Con esta configuración, Apache solicitará un usuario y una contraseña para acceder al directorio.

Comprobamos la sintaxis y recargamos el servicio:

apache2ctl configtest
systemctl reload apache2
Prueba desde terminal con curl

Probar la autenticación básica

Podemos comprobar el acceso a un directorio protegido sin utilizar el navegador.

Primero realizamos una petición sin proporcionar credenciales:

curl -i http://localhost/privado/

Apache debería responder con 401 Unauthorized y solicitar autenticación.

Después repetimos la petición proporcionando un usuario y contraseña: 

curl -i -u alumno http://localhost/privado/

curl solicitará la contraseña por terminal. Si las credenciales son correctas y el usuario tiene permiso, recibiremos una respuesta satisfactoria, normalmente 200 OK.

También podemos consultar las cabeceras sin mostrar el contenido de la página: 

curl -I -u alumno http://localhost/privado/

4.4. Restricciones por dirección IP

Además de la autenticación, Apache permite restringir el acceso a determinados recursos según la dirección IP del cliente.

Ejemplo 2

Permitir el acceso únicamente desde una IP

<Directory /var/www/empresa/privado>
    Require ip 192.168.1.100
</Directory>

También podemos permitir el acceso a una red completa: 

<Directory /var/www/empresa/privado>
    Require ip 192.168.1.0/24
</Directory>

En este caso, solamente los equipos de esa red podrán acceder al directorio.

4.5. Permisos del sistema de archivos

La autenticación HTTP no sustituye a los permisos del sistema de archivos. Apache también necesita permisos adecuados para leer los recursos publicados.

El archivo de contraseñas debe encontrarse fuera del directorio público y ser legible por el proceso de Apache, sin permitir su modificación por usuarios no autorizados.

5. HTTPS y certificados digitales

5.1. Funcionamiento de HTTPS

HTTPS es la versión segura del protocolo HTTP. Utiliza TLS para cifrar las comunicaciones entre el navegador y el servidor.

HTTPS proporciona principalmente:

  • Confidencialidad: los datos transmitidos están cifrados.
  • Integridad: permite detectar modificaciones de los datos.
  • Autenticación: permite comprobar la identidad del servidor mediante un certificado.

El protocolo HTTPS utiliza habitualmente el puerto 443, mientras que HTTP utiliza el puerto 80.

5.2. Certificados digitales

Un certificado digital permite asociar una identidad con una clave pública. Los navegadores utilizan estos certificados para verificar la identidad del servidor.

Podemos distinguir dos tipos habituales de certificados:

  • Certificados autofirmados: generados por el propio administrador. Son útiles en laboratorios y entornos de pruebas.
  • Certificados emitidos por una autoridad certificadora: permiten que los navegadores confíen en el servidor si la autoridad está reconocida.

5.3. Crear un certificado autofirmado

Para habilitar HTTPS en un entorno de pruebas podemos generar un certificado autofirmado utilizando OpenSSL.

Primero instalamos OpenSSL:

apt install openssl
Ejemplo 1

Generar una clave privada y un certificado

Creamos un directorio para almacenar los certificados: 

mkdir -p /etc/apache2/ssl

Generamos una clave privada y un certificado autofirmado incluyendo el nombre del servidor: 

openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
-keyout /etc/apache2/ssl/empresa.key \
-out /etc/apache2/ssl/empresa.crt \
-subj "/C=ES/ST=Galicia/L=A Coruna/O=Empresa/OU=IT/CN=empresa.local" \
-addext "subjectAltName=DNS:empresa.local"

Se generan dos archivos:

  • empresa.key: clave privada.
  • empresa.crt: certificado digital.

La clave privada debe mantenerse protegida y no debe compartirse con los clientes.

5.4. Configurar Apache para utilizar HTTPS

Primero habilitamos el módulo SSL: 

a2enmod ssl
systemctl reload apache2
Ejemplo 2

Crear un VirtualHost HTTPS

Creamos un archivo de configuración para el sitio seguro, por ejemplo: /etc/apache2/sites-available/empresa-ssl.conf. 

<VirtualHost *:443>
    ServerName empresa.local

    DocumentRoot /var/www/empresa

    SSLEngine on
    SSLCertificateFile /etc/apache2/ssl/empresa.crt
    SSLCertificateKeyFile /etc/apache2/ssl/empresa.key

    <Directory /var/www/empresa>
        Options -Indexes
        AllowOverride None
        Require all granted
    </Directory>

    ErrorLog ${APACHE_LOG_DIR}/empresa_ssl_error.log
    CustomLog ${APACHE_LOG_DIR}/empresa_ssl_access.log combined
</VirtualHost>

Habilitamos el sitio y comprobamos la configuración: 

a2ensite empresa-ssl.conf
apache2ctl configtest
systemctl reload apache2

Podemos acceder al sitio utilizando: 

https://empresa.local/
Prueba desde terminal con curl

Comprobar una conexión HTTPS

Podemos realizar una petición HTTPS para comprobar que Apache está atendiendo peticiones cifradas. 

curl -I https://localhost/

Si utilizamos un certificado autofirmado, es posible que curl muestre un error de validación del certificado.

Para realizar una prueba ignorando temporalmente esa validación: 

curl -k -I https://localhost/

La opción -k permite aceptar certificados no verificados. Debe utilizarse únicamente en pruebas.

También podemos consultar la respuesta completa:

curl -k -i https://localhost/

Para probar el nombre del VirtualHost y el certificado correspondiente podemos utilizar: 

curl -k -i --resolve empresa.local:443:127.0.0.1 \
https://empresa.local/

5.5. Redirigir HTTP hacia HTTPS

Una vez configurado HTTPS, podemos hacer que las peticiones HTTP se redirijan automáticamente a la versión segura del sitio.

Ejemplo 3

Redirección permanente a HTTPS

En el VirtualHost del puerto 80 podemos añadir: 

<VirtualHost *:80>
    ServerName empresa.local

    Redirect permanent / https://empresa.local/
</VirtualHost>

De esta forma, las peticiones realizadas mediante HTTP recibirán una redirección permanente hacia HTTPS.

Prueba desde terminal con curl

Comprobar la redirección HTTP a HTTPS

Consultamos las cabeceras de la respuesta HTTP: 

curl -I http://localhost/

Si la redirección está configurada correctamente, recibiremos una respuesta similar a: 

HTTP/1.1 301 Moved Permanently
Location: https://empresa.local/

Podemos seguir la redirección automáticamente: 

curl -k -L -i http://localhost/

5.6. Certificados de Let's Encrypt

En servidores accesibles desde Internet podemos utilizar certificados gratuitos emitidos por Let's Encrypt. Estos certificados son reconocidos por los principales navegadores.

Una herramienta habitual para gestionar estos certificados es Certbot. 

apt install certbot python3-certbot-apache

Para solicitar y configurar un certificado: 

certbot --apache -d ejemplo.com

Este procedimiento requiere disponer de un dominio válido y que el servidor cumpla los requisitos de validación de Let's Encrypt. No es una alternativa adecuada para los nombres locales del laboratorio, como empresa.local.

6. Resumen: pruebas con curl

La herramienta curl permite realizar peticiones HTTP y HTTPS desde la terminal. Es especialmente útil para comprobar la configuración de Apache sin necesidad de utilizar un navegador.

Comprobación Comando
Consultar cabeceras HTTP curl -I http://localhost/
Consultar respuesta completa curl -i http://localhost/
Seguir redirecciones curl -L -i http://localhost/antigua
Probar un VirtualHost curl -i -H "Host: empresa.local" http://localhost/
Probar autenticación HTTP curl -i -u alumno http://localhost/privado/
Probar HTTPS curl -k -I https://localhost/
Probar HTTPS con nombre de dominio curl -k --resolve empresa.local:443:127.0.0.1 https://empresa.local/
Consultar cabeceras de seguridad curl -I http://localhost/
Conocimiento clave

curl permite probar el servidor directamente desde Debian. El navegador de la máquina física permite comprobar el acceso desde otro equipo.

Ambas pruebas son complementarias: una configuración puede funcionar en localhost y presentar problemas de red, firewall o NAT al acceder desde el exterior.

Para las pruebas locales, Apache debe estar escuchando en el puerto 80 o 443, según corresponda. Si se utiliza otro puerto, habrá que indicarlo en la URL, por ejemplo: http://localhost:8080/.
