Bloque 1. Arquitectura, configuración y administración de aplicaciones

En este bloque se estudia el funcionamiento de los servidores de aplicaciones, su arquitectura, la instalación y configuración de Apache Tomcat y los mecanismos utilizados para desplegar y administrar aplicaciones web.

1. Arquitectura y funcionamiento de los servidores de aplicaciones

1.1. ¿Qué es un servidor de aplicaciones?

Un servidor de aplicaciones es un software que proporciona un entorno de ejecución para aplicaciones, especialmente aplicaciones web. Se encarga de ejecutar la lógica de negocio, gestionar las peticiones de los usuarios y proporcionar servicios necesarios para el funcionamiento de las aplicaciones.

Entre sus principales funciones se encuentran:

  • Procesar las peticiones de los clientes.
  • Ejecutar la lógica de las aplicaciones.
  • Gestionar sesiones de usuario.
  • Administrar conexiones con bases de datos.
  • Gestionar componentes web y recursos compartidos.
  • Proporcionar mecanismos de seguridad y autenticación.

1.2. Diferencias entre servidor web y servidor de aplicaciones

Aunque ambos servidores participan en el funcionamiento de una aplicación web, sus responsabilidades son diferentes.

Servidor web Servidor de aplicaciones
Entrega contenido estático. Ejecuta la lógica de las aplicaciones.
Procesa peticiones HTTP. Procesa peticiones que requieren ejecución de código.
Sirve HTML, CSS, JavaScript e imágenes. Ejecuta servlets, JSP y otros componentes.
Ejemplo: Apache HTTP Server. Ejemplo: Apache Tomcat.

1.3. Arquitectura de una aplicación web

En una arquitectura habitual, el navegador del usuario realiza una petición HTTP al servidor web. Este puede responder directamente si se solicita un recurso estático o reenviar la petición al servidor de aplicaciones si necesita ejecutar código.

Ejemplo de arquitectura: 
NAVEGADOR DEL CLIENTE
        |
        | Petición HTTP
        v
APACHE HTTP SERVER
        |
        | Reenvío de peticiones dinámicas
        v
APACHE TOMCAT
        |
        | Ejecución de la aplicación
        v
BASE DE DATOS

Esta separación permite distribuir responsabilidades, mejorar la organización y facilitar la administración de los servicios.

1.4. Introducción a Apache Tomcat

Apache Tomcat es un servidor web y contenedor de aplicaciones Java que implementa tecnologías como Jakarta Servlet y Jakarta Server Pages (JSP).

Sus principales características son:

  • Permite ejecutar aplicaciones web Java.
  • Implementa las especificaciones Servlet y JSP.
  • Proporciona gestión de sesiones.
  • Permite configurar usuarios y roles.
  • Incluye un servidor HTTP integrado.
  • Permite desplegar aplicaciones mediante archivos WAR.

Tomcat no es un servidor de aplicaciones Java EE/Jakarta EE completo: implementa principalmente las tecnologías web Servlet y JSP, no todo el conjunto de servicios empresariales.

Concepto importante: Tomcat incorpora su propio servidor HTTP, por lo que puede funcionar de manera independiente sin necesidad de instalar Apache HTTP Server.

1.5. Ejemplo de funcionamiento

Cuando un usuario solicita una página dinámica, Tomcat recibe la petición, identifica el recurso solicitado, ejecuta el componente correspondiente y devuelve una respuesta HTTP. 

Cliente:
http://localhost:8080/miaplicacion/hola

Tomcat:
1. Recibe la petición.
2. Localiza la aplicación.
3. Ejecuta el servlet correspondiente.
4. Genera una respuesta.
5. Devuelve el contenido al navegador.

2. Instalación y configuración básica de Tomcat

2.1. Instalación de Apache Tomcat en Debian

Tomcat puede instalarse utilizando los repositorios de Debian o descargando una distribución desde la página oficial del proyecto.

Para instalar Tomcat desde los repositorios:

apt update
apt install tomcat10

La versión disponible depende de la distribución y sus repositorios. También es posible instalar una versión concreta desde la página oficial:

https://tomcat.apache.org/

Para comprobar el estado del servicio: 

systemctl status tomcat10

Para iniciar, detener y reiniciar el servidor:

systemctl start tomcat10
systemctl stop tomcat10
systemctl restart tomcat10

Para activar el inicio automático:

systemctl enable tomcat10

2.2. Comprobación del funcionamiento

Por defecto, Tomcat utiliza el puerto TCP 8080 para atender las peticiones HTTP. Una vez iniciado el servicio, se puede acceder desde un navegador: 

http://localhost:8080

También podemos comprobar la respuesta utilizando curl: 

curl -I http://localhost:8080

2.3. Estructura de directorios

Tomcat organiza sus archivos en diferentes directorios. Su ubicación concreta depende del método de instalación.

Directorio Función
bin/ Scripts de inicio, parada y administración.
conf/ Archivos de configuración del servidor.
lib/ Bibliotecas compartidas utilizadas por Tomcat.
logs/ Registros de actividad y errores.
webapps/ Aplicaciones web desplegadas.
work/ Archivos temporales generados durante la ejecución.
temp/ Archivos temporales del servidor.

2.4. Archivos principales de configuración

Los archivos de configuración permiten modificar el comportamiento del servidor. Se encuentran principalmente en el directorio conf/.

Archivo Descripción
server.xml Configuración general, conectores, puertos y servicios.
web.xml Configuración predeterminada de las aplicaciones web.
tomcat-users.xml Usuarios y roles utilizados por las aplicaciones de administración.
context.xml Configuración de contextos y recursos de las aplicaciones.
logging.properties Configuración del sistema de registros.

2.5. Configuración de puertos

El archivo server.xml contiene los conectores que permiten a Tomcat recibir peticiones de los clientes.

Ejemplo de un conector HTTP:

<Connector
    port="8080"
    protocol="HTTP/1.1"
    connectionTimeout="20000"
    redirectPort="8443" />

En este ejemplo, Tomcat escucha las peticiones HTTP en el puerto 8080. El puerto 8443 se utiliza habitualmente como destino de redirección para conexiones que requieren HTTPS.

Importante: Después de modificar server.xml, es necesario reiniciar Tomcat para aplicar los cambios.

2.6. Bibliotecas compartidas

Tomcat utiliza bibliotecas Java para proporcionar sus funcionalidades. Estas bibliotecas se almacenan principalmente en el directorio lib/.

También es posible incorporar bibliotecas específicas dentro de cada aplicación web, normalmente en el directorio WEB-INF/lib/.

  • lib/: bibliotecas compartidas por el servidor y las aplicaciones.
  • WEB-INF/lib/: bibliotecas propias de una aplicación.
  • WEB-INF/classes/: clases Java compiladas de la aplicación.

2.7. Registros del servidor

Los logs permiten conocer el funcionamiento de Tomcat y detectar errores. Pueden consultarse desde el directorio logs/.

En instalaciones de Debian también podemos utilizar:

journalctl -u tomcat10
journalctl -u tomcat10 -f

El segundo comando permite visualizar los mensajes nuevos a medida que se generan.

Ejercicios prácticos

  1. Instala Tomcat en Debian y comprueba que el servicio está activo.
  2. Accede a la página principal desde el navegador.
  3. Identifica los directorios principales de la instalación.
  4. Localiza el archivo server.xml y comprueba el puerto HTTP configurado.
  5. Consulta los registros del servidor y localiza los mensajes de inicio.
  6. Investiga qué ocurre si intentas iniciar dos servicios que utilizan el mismo puerto.

3. Administración y despliegue de aplicaciones web

3.1. ¿Qué significa desplegar una aplicación?

Desplegar una aplicación web consiste en instalarla y configurarla en un servidor para que pueda ser utilizada por los clientes.

El proceso normalmente incluye:

  1. Preparar y compilar la aplicación.
  2. Generar el paquete de despliegue.
  3. Copiarlo al servidor.
  4. Configurar los recursos necesarios.
  5. Iniciar o recargar la aplicación.
  6. Comprobar que funciona correctamente.

3.2. Estructura de una aplicación web Java

Una aplicación web Java sigue una estructura organizada que separa los recursos públicos, las clases Java y las bibliotecas. 

miaplicacion/
│
├── index.html
├── css/
│   └── estilos.css
│
└── WEB-INF/
    ├── web.xml
    ├── classes/
    │   └── es/
    │       └── centro/
    │           └── MiServlet.class
    │
    └── lib/
        └── biblioteca.jar

El directorio WEB-INF contiene recursos internos de la aplicación. No se puede acceder directamente a su contenido mediante una petición HTTP.

3.3. Archivos WAR

WAR (Web Application Archive) es el formato de distribución habitual de las aplicaciones web Java.

Se trata de un archivo comprimido que contiene la estructura de directorios y los recursos necesarios para ejecutar la aplicación.

Podemos identificar su contenido con:

jar -tf aplicacion.war

Para generar un archivo WAR a partir de una estructura de aplicación: 

jar -cvf miaplicacion.war -C miaplicacion .

3.4. Despliegue mediante el directorio webapps

Tomcat permite desplegar aplicaciones copiando su directorio o archivo WAR en webapps/.

Ejemplo:

cp miaplicacion.war /var/lib/tomcat10/webapps/

Si la instalación utiliza el despliegue automático, Tomcat detectará el archivo WAR y lo expandirá.

La aplicación estará disponible normalmente en: 

http://localhost:8080/miaplicacion/

El nombre del archivo WAR determina normalmente el nombre del contexto. Por ejemplo, miaplicacion.war se publica bajo /miaplicacion.

3.5. Actualización de aplicaciones

Cuando se modifica una aplicación, es necesario sustituir su versión desplegada por la nueva.

Un procedimiento habitual consiste en:

  1. Preparar una copia de seguridad de la versión actual.
  2. Detener o retirar la aplicación si la configuración lo requiere.
  3. Sustituir el archivo WAR.
  4. Comprobar que Tomcat ha desplegado la nueva versión.
  5. Realizar pruebas de funcionamiento.

Ejemplo de sustitución de un archivo WAR: 

cp miaplicacion.war /var/lib/tomcat10/webapps/

Es recomendable comprobar los registros si la aplicación no se actualiza correctamente.

3.6. Retirada de aplicaciones

Para eliminar una aplicación desplegada mediante un WAR, debemos retirar el archivo y su directorio expandido, cuando exista. 

rm /var/lib/tomcat10/webapps/miaplicacion.war
rm -r /var/lib/tomcat10/webapps/miaplicacion

Hay que tener en cuenta que la eliminación manual debe realizarse con precaución y respetando los permisos del usuario del servicio.

3.7. Administración mediante Manager

Tomcat incorpora una aplicación de administración denominada Manager, que permite gestionar aplicaciones web desde una interfaz HTTP.

Entre sus funciones destacan:

  • Desplegar aplicaciones.
  • Iniciar y detener aplicaciones.
  • Recargar aplicaciones.
  • Retirar aplicaciones.
  • Consultar información sobre los despliegues.

Para utilizar Manager es necesario configurar usuarios y roles adecuados. Por motivos de seguridad, no debe exponerse esta interfaz públicamente sin restricciones.

Ejercicios prácticos

  1. Localiza el directorio webapps de Tomcat.
  2. Despliega una aplicación web sencilla mediante un archivo WAR.
  3. Accede a la aplicación desde el navegador.
  4. Modifica su contenido y vuelve a desplegarla.
  5. Comprueba qué sucede cuando se elimina el archivo WAR.
  6. Investiga las funciones disponibles en Tomcat Manager.

4. Componentes web y configuración de aplicaciones

4.1. Componentes de una aplicación web Java

Las aplicaciones web Java utilizan diferentes componentes para procesar peticiones, generar respuestas y proporcionar contenido dinámico.

Los principales componentes son:

  • Servlets: componentes Java que procesan peticiones HTTP.
  • JSP: páginas que permiten generar contenido dinámico.
  • Filtros: componentes que interceptan peticiones y respuestas.
  • Listeners: componentes que reaccionan ante eventos de la aplicación.

4.2. Servlets

Un servlet es una clase Java ejecutada por el contenedor web que permite procesar peticiones y generar respuestas HTTP.

Tomcat recibe la petición y delega su procesamiento al servlet correspondiente.

Ejemplo sencillo de servlet:

package es.centro;

import java.io.IOException;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

public class MiServlet extends HttpServlet {

    @Override
    protected void doGet(
        HttpServletRequest request,
        HttpServletResponse response
    ) throws ServletException, IOException {

        response.setContentType("text/html;charset=UTF-8");

        response.getWriter().println(
            "<h1>Hola desde Tomcat</h1>"
        );
    }
}

El método doGet() procesa peticiones HTTP GET. Para procesar peticiones POST se utiliza doPost().

4.3. Páginas JSP

JSP (Jakarta Server Pages) permite crear páginas web dinámicas utilizando HTML y elementos Java.

Tomcat transforma las páginas JSP en servlets y las ejecuta.

Ejemplo de una página JSP:

<%@ page contentType="text/html;charset=UTF-8" %>
<!DOCTYPE html>
<html>
<head>
    <title>Ejemplo JSP</title>
</head>
<body>

    <h1>Aplicación web Java</h1>

    <p>Fecha y hora del servidor:</p>

    <%= new java.util.Date() %>

</body>
</html>

4.4. Configuración mediante web.xml

El archivo web.xml permite definir configuraciones específicas de una aplicación web.

Entre sus posibilidades se encuentran:

  • Declarar servlets.
  • Asociar URL con servlets.
  • Definir páginas de inicio.
  • Configurar tiempos de sesión.
  • Definir filtros y mecanismos de seguridad.
  • Establecer páginas de error.

Ejemplo de configuración:

<?xml version="1.0" encoding="UTF-8"?>

<web-app xmlns="https://jakarta.ee/xml/ns/jakartaee"
         version="6.0">

    <servlet>
        <servlet-name>MiServlet</servlet-name>
        <servlet-class>es.centro.MiServlet</servlet-class>
    </servlet>

    <servlet-mapping>
        <servlet-name>MiServlet</servlet-name>
        <url-pattern>/hola</url-pattern>
    </servlet-mapping>

    <welcome-file-list>
        <welcome-file>index.html</welcome-file>
    </welcome-file-list>

</web-app>

En este ejemplo, el servlet MiServlet responde a las peticiones dirigidas a la ruta /hola.

La URL completa será:

http://localhost:8080/miaplicacion/hola

4.5. Contextos de aplicación

Un contexto identifica una aplicación web dentro de Tomcat. Cada aplicación dispone de su propio espacio de nombres y configuración.

Por ejemplo, si Tomcat tiene desplegadas las aplicaciones tienda y centro, sus direcciones serán: 

http://localhost:8080/tienda/
http://localhost:8080/centro/

El contexto también permite definir recursos y parámetros específicos de una aplicación.

4.6. Recursos de las aplicaciones

Las aplicaciones pueden necesitar recursos externos para funcionar, como conexiones a bases de datos, bibliotecas o archivos de configuración.

Tomcat permite definir recursos mediante elementos de configuración específicos.

Ejemplo conceptual de un recurso de conexión JDBC:

<Resource
    name="jdbc/centro"
    auth="Container"
    type="javax.sql.DataSource"
    driverClassName="org.mariadb.jdbc.Driver"
    url="jdbc:mariadb://localhost:3306/centro"
    username="aplicacion"
    password="clave"
    maxTotal="20"
    maxIdle="10" />

Este recurso representa un conjunto de conexiones a una base de datos MariaDB. Para utilizarlo es necesario instalar el controlador JDBC correspondiente y configurar correctamente su ámbito.

Importante: Las credenciales de conexión no deben almacenarse en repositorios públicos. En entornos reales deben utilizarse mecanismos seguros para gestionar los secretos y las contraseñas.

4.7. Ciclo de vida de una aplicación

Cuando Tomcat despliega una aplicación, realiza una serie de operaciones:

  1. Localiza el archivo WAR o el directorio de la aplicación.
  2. Comprueba su estructura y configuración.
  3. Carga las clases y bibliotecas necesarias.
  4. Inicializa los componentes web.
  5. Registra los servlets y sus rutas.
  6. Comienza a atender peticiones.

Cuando se retira la aplicación, Tomcat libera los recursos asociados y deja de atender peticiones para ese contexto.

  4. Modifica una configuración para establecer una página de inicio.
  5. Define un servlet llamado SaludoServlet asociado a la ruta /saludo.
  6. Despliega dos aplicaciones diferentes en Tomcat y comprueba sus contextos.
  7. Investiga cómo se configura un recurso JDBC para acceder a MariaDB.
