Seguridad, despliegue y monitorización de aplicaciones web

Hardening de servidores Apache, despliegue de aplicaciones web, virtualización, Docker, gestión de registros y monitorización.

6. Seguridad avanzada y documentación del servidor

6.1. ¿Qué es el hardening?

El hardening o endurecimiento de un servidor consiste en aplicar medidas de seguridad para reducir las posibilidades de que un atacante pueda comprometer el sistema.

Un servidor web no es seguro únicamente por utilizar HTTPS. También es necesario configurar correctamente los permisos, desactivar funcionalidades innecesarias, mantener el software actualizado y limitar los accesos.

Los objetivos principales del hardening son:

  • Reducir la superficie de ataque.
  • Limitar los privilegios de usuarios y procesos.
  • Evitar la exposición de información sensible.
  • Mantener el software actualizado.
  • Registrar los accesos y errores.
  • Facilitar la recuperación ante incidentes.

6.2. Principio de mínimo privilegio

El principio de mínimo privilegio establece que cada usuario, proceso o servicio debe disponer únicamente de los permisos necesarios para realizar su función.

Por ejemplo, un servidor Apache que publica archivos HTML necesita leerlos, pero normalmente no necesita modificarlos.

Podemos comprobar los permisos de un directorio web con:

ls -ld /var/www/html
ls -l /var/www/html
Ejemplo 1

Configurar permisos para una web estática

Una configuración habitual para una web estática consiste en asignar la propiedad de los archivos a root y permitir su lectura por el resto de usuarios: 

chown -R root:root /var/www/html

find /var/www/html -type d -exec chmod 755 {} \;

find /var/www/html -type f -exec chmod 644 {} \;

Estos permisos permiten leer los archivos y atravesar los directorios, pero reservan la escritura al propietario.

Importante

Esta configuración es apropiada para contenido estático que no necesita ser modificado por Apache.

Una aplicación dinámica puede necesitar permisos específicos sobre determinados directorios, por ejemplo para cargar archivos o almacenar datos. No debemos aplicar estos comandos indiscriminadamente a cualquier aplicación.

6.3. Ocultar información innecesaria

Apache puede revelar información sobre el servidor en determinadas respuestas HTTP. Podemos reducir parte de esta exposición mediante las siguientes directivas: 

ServerTokens Prod
ServerSignature Off
  • ServerTokens Prod: reduce la información de versión que aparece en la cabecera Server.
  • ServerSignature Off: desactiva la firma informativa que Apache puede mostrar en páginas generadas por el servidor.

Estas medidas dificultan la identificación de algunos detalles de la instalación, pero no sustituyen a las actualizaciones ni a la corrección de vulnerabilidades.

Ejemplo 2

Aplicar las directivas de seguridad

Podemos incorporar las directivas en la configuración global de Apache y comprobar que no existen errores: 

apache2ctl configtest
systemctl reload apache2

6.4. Controlar el acceso a los directorios

No todos los directorios de una aplicación deben ser accesibles desde Internet.

Por ejemplo, no debemos publicar directamente directorios que contengan copias de seguridad, archivos de configuración, credenciales o código que no deba descargarse.

Ejemplo 3

Configurar un directorio público

Una configuración básica para un directorio público sería: 

<Directory /var/www/html>
    Options -Indexes
    AllowOverride None
    Require all granted
</Directory>

Esta configuración:

  • Desactiva los listados automáticos de directorios.
  • Impide que los archivos .htaccess sobrescriban la configuración en ese directorio.
  • Permite el acceso HTTP a los recursos del directorio.
Ejemplo 4

Restringir el acceso a un directorio administrativo

Para un directorio administrativo podemos establecer una restricción por dirección IP: 

<Directory /var/www/html/admin>
    Options -Indexes
    AllowOverride None
    Require ip 192.168.1.0/24
</Directory>

Esta regla limita el acceso a la red indicada. La dirección de red debe adaptarse a la infraestructura real.

6.5. Mantener el servidor actualizado

Las actualizaciones corrigen errores, solucionan vulnerabilidades y mejoran la estabilidad del sistema.

En Debian podemos actualizar los índices e instalar las actualizaciones disponibles:

apt update
apt upgrade

Antes de realizar actualizaciones en producción conviene:

  1. Revisar los cambios y sus posibles incompatibilidades.
  2. Realizar copias de seguridad.
  3. Probar las actualizaciones en un entorno de pruebas cuando sea posible.
  4. Aplicarlas en una ventana de mantenimiento adecuada.
  5. Comprobar el funcionamiento del servidor después de la actualización.

También debemos revisar periódicamente los módulos habilitados y desactivar los que no sean necesarios.

6.6. Protección de las comunicaciones

Para proteger las comunicaciones entre el cliente y el servidor debemos utilizar HTTPS con una configuración TLS adecuada.

Las principales medidas son:

  • Utilizar certificados válidos para los nombres de dominio publicados.
  • Proteger la clave privada del certificado.
  • Mantener actualizados Apache y las bibliotecas criptográficas.
  • Evitar protocolos y algoritmos obsoletos.
  • Redirigir HTTP a HTTPS cuando corresponda.
  • Renovar los certificados antes de que caduquen.
  • Evitar transmitir credenciales y datos sensibles por conexiones sin cifrar.
Ejemplo 5

Comprobar el certificado de un servidor

Para comprobar el certificado presentado por un servidor podemos utilizar OpenSSL: 

openssl s_client \
    -connect ejemplo.com:443 \
    -servername ejemplo.com

El nombre ejemplo.com debe sustituirse por el dominio real del servidor.

6.7. Copias de seguridad

Una copia de seguridad permite recuperar la configuración y los datos después de un fallo, un borrado accidental o un incidente de seguridad.

En un servidor Apache debemos considerar, como mínimo:

  • /etc/apache2/: configuración del servidor.
  • /var/www/: contenido web, si se encuentra en esa ubicación.
  • Certificados y claves necesarios, con protección especial para las claves privadas.
  • Bases de datos y archivos de datos de las aplicaciones.
  • Archivos de configuración de servicios auxiliares.
Ejemplo 6

Realizar una copia de seguridad de Apache

Podemos crear un archivo comprimido con toda la configuración de Apache: 

tar -czf apache-config.tar.gz /etc/apache2

Este comando genera un archivo comprimido con la configuración. La copia debe trasladarse a una ubicación adecuada, con acceso restringido, y no debería almacenarse únicamente en el mismo disco del servidor.

Una estrategia de copias de seguridad debe contemplar también la frecuencia, la retención, la ubicación externa y las pruebas periódicas de restauración.

6.8. Documentación técnica del servidor

La documentación permite conocer cómo está configurado el servidor, facilita su mantenimiento y ayuda a otros administradores a reproducir la instalación.

Una documentación técnica debería incluir:

Apartado Información que debe contener
Identificación Nombre del servidor, sistema operativo y versión de Apache.
Red Dirección IP, nombres de dominio y puertos utilizados.
Configuración Archivos principales y directivas modificadas.
Sitios virtuales Dominios, directorios raíz y archivos de configuración.
Seguridad Certificados, autenticación, permisos y restricciones.
Aplicaciones Tecnologías utilizadas, dependencias y procedimiento de despliegue.
Registros Ubicación de los logs y procedimientos de análisis.
Copias de seguridad Qué se copia, cuándo y cómo se restaura.
Mantenimiento Actualizaciones, renovaciones y comprobaciones periódicas.
Importante

No se deben incluir contraseñas, claves privadas ni otros secretos directamente en el documento. Es preferible indicar dónde se almacenan de forma segura y quién tiene acceso.

7. Despliegue de aplicaciones web

7.1. ¿Qué significa desplegar una aplicación?

Desplegar una aplicación web consiste en instalarla y configurarla en un servidor para que los usuarios puedan acceder a ella.

El proceso no consiste únicamente en copiar archivos. También puede requerir instalar dependencias, configurar variables de entorno, preparar una base de datos, establecer permisos, habilitar HTTPS y comprobar el funcionamiento.

Las tareas habituales son:

  1. Preparar el servidor.
  2. Instalar las dependencias.
  3. Copiar o descargar la aplicación.
  4. Configurar la aplicación.
  5. Preparar la base de datos, si existe.
  6. Ajustar los permisos.
  7. Configurar Apache.
  8. Realizar pruebas.
  9. Revisar los registros y documentar el despliegue.

7.2. Tipos de aplicaciones web

Podemos distinguir varios tipos de aplicaciones:

Aplicaciones estáticas

Están formadas principalmente por HTML, CSS, JavaScript e imágenes. Apache puede servirlas directamente.

Aplicaciones dinámicas

Generan contenido en función de los datos, las peticiones o la sesión del usuario. Pueden utilizar PHP, Python, Java, Node.js u otras tecnologías.

Aplicaciones con base de datos

Necesitan conectarse a un sistema gestor de bases de datos como MySQL o PostgreSQL.

Conocimiento clave

Cada tecnología requiere una configuración específica. Por ejemplo, instalar Apache no es suficiente para ejecutar una aplicación PHP si el entorno PHP necesario no está instalado y configurado.

7.3. Desplegar una aplicación estática

Vamos a desplegar una web sencilla en Debian.

Ejemplo 1

Crear una aplicación web estática

Primero creamos el directorio de publicación:

mkdir -p /var/www/empresa

Creamos el archivo principal:

nano /var/www/empresa/index.html

Contenido del archivo:

<!DOCTYPE html>
<html lang="es">
<head>
    <meta charset="UTF-8">
    <title>Mi aplicación</title>
</head>
<body>
    <h1>Aplicación desplegada</h1>
    <p>El servidor Apache está funcionando.</p>
</body>
</html>

Configuramos los permisos para una web estática: 

chown -R root:root /var/www/empresa

find /var/www/empresa -type d -exec chmod 755 {} \;

find /var/www/empresa -type f -exec chmod 644 {} \;

Después configuramos un sitio virtual:

Ejemplo 2

Configurar el VirtualHost de la aplicación

<VirtualHost *:80>
    ServerName empresa.local
    DocumentRoot /var/www/empresa

    <Directory /var/www/empresa>
        Options -Indexes
        AllowOverride None
        Require all granted
    </Directory>

    ErrorLog ${APACHE_LOG_DIR}/empresa_error.log
    CustomLog ${APACHE_LOG_DIR}/empresa_access.log combined
</VirtualHost>

Guardamos el archivo en /etc/apache2/sites-available/empresa.conf y habilitamos el sitio: 

a2ensite empresa.conf
apache2ctl configtest
systemctl reload apache2

Si el nombre empresa.local está correctamente configurado en el sistema de resolución de nombres del cliente, podremos acceder a: 

http://empresa.local
Prueba desde terminal con curl

Comprobar el despliegue de la aplicación

Desde Debian podemos comprobar el funcionamiento del sitio utilizando la cabecera Host: 

curl -i -H "Host: empresa.local" http://localhost/

También podemos comprobar únicamente las cabeceras: 

curl -I -H "Host: empresa.local" http://localhost/

Si el despliegue es correcto, deberíamos obtener una respuesta 200 OK.

7.4. Despliegue de aplicaciones dinámicas

Las aplicaciones dinámicas necesitan un entorno de ejecución adecuado.

Por ejemplo, para una aplicación PHP con Apache podemos instalar los componentes necesarios con: 

apt install php libapache2-mod-php php-mysql

Los paquetes tienen las siguientes funciones:

  • php: instala el intérprete de PHP.
  • libapache2-mod-php: permite integrar PHP con Apache mediante su módulo correspondiente.
  • php-mysql: proporciona soporte para conectarse a MySQL o MariaDB.

Las necesidades exactas dependen de la aplicación y de la versión de PHP requerida.

Una aplicación dinámica también puede ejecutarse mediante un servidor de aplicaciones independiente, utilizando Apache como proxy inverso. En ese caso, la configuración y las dependencias serán diferentes.

7.5. Configuración de la aplicación

Las aplicaciones pueden necesitar parámetros específicos, como:

  • Dirección del servidor de base de datos.
  • Nombre de la base de datos.
  • Usuario de conexión.
  • Claves de API.
  • Modo de ejecución.
  • Directorio de archivos temporales.
  • Configuración de correo electrónico.
  • URL pública de la aplicación.

Estos valores deben configurarse de forma adecuada al entorno.

Importante

Las contraseñas y claves secretas no deben incorporarse al repositorio del código ni publicarse dentro del directorio web.

En una aplicación dinámica, los directorios de carga de archivos, caché o sesiones pueden necesitar permisos de escritura. Es preferible conceder esos permisos solo a los directorios que realmente lo requieran.

7.6. Comprobaciones posteriores al despliegue

Una vez desplegada la aplicación, debemos verificar que funciona correctamente.

Comandos útiles:

apache2ctl configtest
systemctl status apache2
curl -I http://localhost
tail -n 50 /var/log/apache2/error.log

También debemos comprobar:

  • Que la página principal carga correctamente.
  • Que los recursos estáticos se sirven sin errores.
  • Que las rutas de la aplicación funcionan.
  • Que la conexión a la base de datos es correcta.
  • Que los permisos son adecuados.
  • Que HTTPS funciona, si está configurado.
  • Que no se muestran mensajes de error internos al usuario.

  1. Despliega una aplicación estática en Debian.
  2. Crea un sitio virtual para la aplicación.
  3. Configura los permisos de los archivos.
  4. Comprueba el acceso desde un cliente.
  5. Realiza una petición utilizando curl.
  6. Revisa los registros de Apache.
  7. Documenta las operaciones realizadas.

8. Virtualización, contenedores y Docker Compose

8.1. Virtualización y contenedores

La virtualización permite ejecutar entornos informáticos aislados sobre una misma infraestructura física.

Existen dos enfoques frecuentes:

Máquinas virtuales

Una máquina virtual ejecuta un sistema operativo completo sobre un hipervisor. Cada máquina dispone de recursos virtualizados, como CPU, memoria, almacenamiento y red.

Contenedores

Un contenedor ejecuta una aplicación y sus dependencias de forma aislada, compartiendo el kernel del sistema operativo anfitrión.

Conocimiento clave

Los contenedores suelen ser más ligeros que las máquinas virtuales, aunque ambos enfoques tienen usos diferentes y pueden combinarse.

8.2. Conceptos fundamentales de Docker

Docker es una plataforma que permite construir, distribuir y ejecutar aplicaciones en contenedores.

Concepto Descripción
Imagen Plantilla utilizada para crear contenedores.
Contenedor Instancia ejecutable de una imagen.
Dockerfile Archivo con las instrucciones para construir una imagen.
Volumen Mecanismo para conservar datos fuera del ciclo de vida del contenedor.
Red Permite la comunicación entre contenedores y otros servicios.
Registro Servicio que almacena y distribuye imágenes.
Docker Compose Herramienta para definir y gestionar aplicaciones con varios servicios.

Una imagen puede utilizarse para crear varios contenedores. Cada contenedor tiene su propio ciclo de vida, aunque puede compartir redes y volúmenes con otros.

8.3. Instalar y comprobar Docker

En un entorno Debian de laboratorio, una vez instalado Docker desde una fuente adecuada, podemos comprobar su funcionamiento con: 

docker --version
docker compose version
docker run hello-world

La instalación de Docker Engine debe seguir las instrucciones correspondientes a la versión de Debian utilizada y a la fuente de paquetes elegida.

En un entorno de producción, conviene utilizar repositorios oficiales o paquetes gestionados de forma controlada y mantener Docker actualizado.

8.4. Desplegar Apache en un contenedor

Podemos ejecutar Apache mediante una imagen oficial basada en HTTP Server.

Ejemplo 1

Ejecutar un contenedor Apache

docker run -d \
    --name web1 \
    -p 8080:80 \
    httpd:2.4

Significado de las opciones:

  • -d: ejecuta el contenedor en segundo plano.
  • --name web1: asigna el nombre web1.
  • -p 8080:80: publica el puerto 80 del contenedor en el puerto 8080 del anfitrión.
  • httpd:2.4: indica la imagen que se utilizará.

Podemos acceder desde el navegador a:

http://localhost:8080

Si el navegador está en otro equipo, debemos sustituir localhost por la dirección IP del anfitrión Docker y asegurarnos de que el puerto está accesible.

Comandos básicos para gestionar el contenedor:

# Mostrar contenedores en ejecución
docker ps

# Mostrar todos los contenedores
docker ps -a

# Consultar los registros
docker logs web1

# Detener el contenedor
docker stop web1

# Iniciar un contenedor detenido
docker start web1

# Eliminar un contenedor detenido
docker rm web1
Importante

docker rm elimina un contenedor detenido, pero no elimina automáticamente la imagen de la que procede.

Prueba desde terminal con curl

Comprobar Apache dentro del contenedor

Desde la máquina anfitriona podemos comprobar que el puerto publicado responde: 

curl -I http://localhost:8080

Para obtener también el contenido de la página: 

curl -i http://localhost:8080

8.5. Crear una imagen propia con un Dockerfile

Para desplegar nuestra propia web, podemos construir una imagen que incorpore el contenido.

Ejemplo 2

Crear una imagen personalizada de Apache

Creamos un directorio de proyecto:

mkdir web-docker
cd web-docker

Creamos un archivo index.html:

<!DOCTYPE html>
<html lang="es">
<head>
    <meta charset="UTF-8">
    <title>Web en Docker</title>
</head>
<body>
    <h1>Mi web en un contenedor</h1>
    <p>Apache está ejecutándose mediante Docker.</p>
</body>
</html>

Creamos un archivo llamado Dockerfile:

FROM httpd:2.4

COPY index.html /usr/local/apache2/htdocs/index.html

EXPOSE 80

Las instrucciones tienen las siguientes funciones:

  • FROM: define la imagen base.
  • COPY: copia el archivo al directorio de publicación de Apache.
  • EXPOSE: documenta el puerto utilizado por el servicio; por sí solo no publica el puerto en el anfitrión.

Construimos la imagen:

docker build -t mi-web:1.0 .

Ejecutamos el contenedor:

docker run -d \
    --name mi-web \
    -p 8080:80 \
    mi-web:1.0

La web estará disponible en:

http://localhost:8080
Prueba desde terminal con curl

Comprobar la imagen personalizada

Una vez iniciado el contenedor, podemos comprobar que Apache sirve el archivo incorporado en la imagen: 

curl -i http://localhost:8080

Deberíamos encontrar en la respuesta el texto Mi web en un contenedor.

8.6. Volúmenes y persistencia

Los contenedores son reemplazables. Si un contenedor se elimina, los datos escritos exclusivamente en su capa de escritura pueden perderse.

Los volúmenes permiten conservar datos fuera del ciclo de vida de un contenedor.

Ejemplo 3

Montar un directorio del anfitrión

Para una web estática en desarrollo, podemos montar un directorio del anfitrión: 

docker run -d \
    --name web-volumen \
    -p 8080:80 \
    -v "$PWD":/usr/local/apache2/htdocs:ro \
    httpd:2.4

La opción :ro monta el directorio como solo lectura dentro del contenedor.

Esto facilita modificar los archivos del anfitrión sin reconstruir la imagen en cada cambio.

En producción, conviene elegir entre imágenes inmutables, volúmenes o montajes de directorios según las necesidades de la aplicación. Los datos persistentes deben tener una estrategia de copia de seguridad.

8.7. Redes de Docker

Las redes permiten que varios contenedores se comuniquen entre sí.

Por ejemplo, una aplicación web y una base de datos pueden conectarse a una red privada de Docker sin publicar el puerto de la base de datos en el anfitrión.

Podemos consultar las redes disponibles:

docker network ls

Crear una red:

docker network create red-web

Conectar un contenedor a una red:

docker network connect red-web mi-web

En un despliegue real con varios servicios, es preferible definir las redes dentro de Docker Compose para que la infraestructura sea reproducible.

8.8. Docker Compose

Docker Compose permite describir una aplicación formada por varios servicios en un archivo YAML.

Por ejemplo, podemos definir un servidor web Apache con un volumen para el contenido estático.

Ejemplo 4

Desplegar Apache con Docker Compose

Creamos el archivo compose.yaml:

services:
  web:
    image: httpd:2.4
    container_name: web-compose
    ports:
      - "8080:80"
    volumes:
      - ./html:/usr/local/apache2/htdocs:ro
    restart: unless-stopped

Creamos el directorio de contenido:

mkdir -p html

Creamos html/index.html:

<!DOCTYPE html>
<html lang="es">
<head>
    <meta charset="UTF-8">
    <title>Docker Compose</title>
</head>
<body>
    <h1>Servidor web con Docker Compose</h1>
</body>
</html>

Iniciamos el servicio:

docker compose up -d

Consultamos su estado:

docker compose ps

Consultamos los logs:

docker compose logs -f web

Detenemos y eliminamos los recursos del proyecto:

docker compose down

La opción down elimina los contenedores y las redes creadas por Compose para el proyecto, pero normalmente conserva los volúmenes nombrados salvo que se indique lo contrario. Los archivos de la carpeta html permanecen en el anfitrión.

Prueba desde terminal con curl

Comprobar el servicio de Docker Compose

Una vez iniciado el proyecto, podemos comprobar que el servidor web responde: 

curl -i http://localhost:8080

También podemos comprobar el estado del servicio: 

docker compose ps

8.9. Contenedores y nube

Los contenedores también pueden desplegarse en plataformas de nube.

El proceso general suele ser:

  1. Construir la imagen de la aplicación.
  2. Publicar la imagen en un registro.
  3. Crear el servicio o contenedor en la plataforma elegida.
  4. Configurar las variables de entorno y los secretos.
  5. Asignar recursos y establecer las redes.
  6. Configurar el acceso externo y HTTPS.
  7. Configurar el almacenamiento persistente.
  8. Establecer comprobaciones de salud, registros y monitorización.

Una plataforma gestionada puede asumir parte de las tareas de infraestructura, pero sigue siendo necesario controlar los permisos, las actualizaciones, la configuración y los datos.

9. Gestión de logs, monitorización y análisis

Criterio de evaluación: CA2.10 — Instalar, configurar y utilizar herramientas de gestión de logs para su monitorización, consolidación y análisis en tiempo real.

Contenidos: C2.10 — Conjuntos de herramientas de gestión de logs y apoyo a la toma de decisiones.

9.1. ¿Qué son los logs?

Los logs o registros son archivos o eventos que almacenan información sobre el funcionamiento de un sistema.

En un servidor web, permiten conocer qué peticiones se reciben, qué respuestas se generan y qué errores se producen.

Los registros ayudan a:

  • Detectar fallos de configuración.
  • Investigar errores de las aplicaciones.
  • Identificar peticiones sospechosas.
  • Analizar el uso del servidor.
  • Medir la evolución del tráfico.
  • Detectar posibles incidentes de seguridad.

Los logs no sustituyen a las métricas ni a las trazas de una aplicación, aunque las tres fuentes pueden combinarse para obtener una visión más completa del sistema.

9.2. Logs de Apache

En Debian, los registros de Apache se almacenan habitualmente en: 

/var/log/apache2/

Los dos archivos principales son:

Archivo Función
access.log Registra las peticiones recibidas.
error.log Registra errores y otros mensajes del servidor.

Cada sitio virtual puede utilizar sus propios archivos de registro mediante las directivas CustomLog y ErrorLog.

Ejemplo 1

Configurar registros independientes para un VirtualHost

<VirtualHost *:80>
    ServerName empresa.local
    DocumentRoot /var/www/empresa

    ErrorLog ${APACHE_LOG_DIR}/empresa_error.log
    CustomLog ${APACHE_LOG_DIR}/empresa_access.log combined
</VirtualHost>

Esta configuración permite separar los registros de la web de los registros de otros sitios alojados en el mismo servidor.

9.3. Interpretar el registro de accesos

Una línea habitual del formato combined tiene una estructura semejante a esta: 

192.168.1.20 - - [20/Oct/2026:18:30:12 +0200] "GET /index.html HTTP/1.1" 200 1250 "-" "Mozilla/5.0"

Podemos interpretar sus campos de la siguiente manera:

Campo Significado
192.168.1.20 Dirección del cliente registrada por Apache.
Fecha y hora Momento de la petición.
GET Método HTTP utilizado.
/index.html Recurso solicitado.
HTTP/1.1 Versión del protocolo de la petición.
200 Código de respuesta HTTP.
1250 Tamaño de la respuesta en bytes, según el formato de registro.
"-" No se ha registrado un referente en ese campo.
Mozilla/5.0 Cadena de agente de usuario del cliente.
Importante

La dirección registrada no siempre corresponde a la IP original del usuario. Si existen proxies inversos o balanceadores, será necesario interpretar correctamente esa infraestructura.

9.4. Códigos de estado HTTP

Los códigos de estado ayudan a interpretar el resultado de una petición.

Código Significado
200 OK La petición se ha atendido correctamente.
301 Moved Permanently Redirección permanente.
302 Found Redirección temporal en el uso habitual.
400 Bad Request Petición incorrecta.
401 Unauthorized Se requieren credenciales válidas.
403 Forbidden El acceso está prohibido.
404 Not Found El recurso no se encuentra.
500 Internal Server Error Error interno del servidor o de la aplicación.
502 Bad Gateway Un proxy o pasarela ha recibido una respuesta no válida del servidor ascendente.
503 Service Unavailable Servicio temporalmente no disponible.

Una gran cantidad de respuestas 404 puede indicar enlaces rotos, errores de configuración o intentos de búsqueda de recursos inexistentes. No implica necesariamente un ataque.

9.5. Consultar los logs en tiempo real

Podemos utilizar diferentes comandos para consultar los registros de Apache desde la terminal.

Ejemplo 2

Consultar los registros de Apache

Para visualizar las últimas líneas del registro de accesos:

tail -f /var/log/apache2/access.log

Para consultar los errores:

tail -f /var/log/apache2/error.log

Para mostrar las últimas 100 líneas:

tail -n 100 /var/log/apache2/access.log
Ejemplo 3

Buscar respuestas 404

Para buscar respuestas con código 404 en un registro que utilice el formato habitual de Apache: 

grep '" 404 ' /var/log/apache2/access.log
Ejemplo 4

Contar las peticiones por dirección IP

Podemos agrupar las líneas por el primer campo y mostrar primero las direcciones que aparecen con mayor frecuencia: 

awk '{print $1}' /var/log/apache2/access.log | sort | uniq -c | sort -nr

Este comando permite identificar las direcciones IP que aparecen con mayor frecuencia en el registro.

Importante

El resultado debe interpretarse con cuidado: una dirección IP puede corresponder a un proxy, una red compartida o un sistema automatizado legítimo.

9.6. Rotación de logs

Los registros pueden crecer mucho y ocupar espacio en disco.

La rotación de logs permite archivar los registros antiguos, iniciar nuevos archivos y eliminar o comprimir registros que superen una determinada antigüedad.

En Debian suele utilizarse logrotate, que puede configurarse para Apache.

Comprobamos si está instalado:

dpkg -l logrotate

Podemos revisar la configuración específica:

cat /etc/logrotate.d/apache2
Ejemplo 5

Ejemplo de configuración de logrotate

/var/log/apache2/*.log {
    daily
    missingok
    rotate 14
    compress
    delaycompress
    notifempty
    create 640 root adm
    sharedscripts
    postrotate
        if pgrep -x apache2 > /dev/null; then
            systemctl reload apache2 > /dev/null 2>&1 || true
        fi
    endscript
}

En esta configuración:

  • daily: solicita una rotación diaria.
  • rotate 14: conserva hasta 14 archivos rotados.
  • compress: comprime los archivos rotados.
  • delaycompress: retrasa la compresión del archivo más reciente.
  • notifempty: no rota archivos vacíos.
  • create: define los permisos y el propietario de los nuevos archivos.

La política exacta depende de la distribución, el volumen de tráfico y las necesidades de conservación. Es preferible revisar la configuración ya proporcionada por Debian antes de modificarla.

9.7. Monitorización del servidor

La monitorización consiste en observar el estado del sistema de manera continuada para detectar problemas y conocer su rendimiento.

Podemos monitorizar diferentes aspectos:

Elemento Qué se puede observar
CPU Uso del procesador.
Memoria Memoria disponible y consumo de los procesos.
Disco Espacio libre y crecimiento de los logs.
Red Tráfico, conexiones y errores de comunicación.
Apache Estado del servicio, peticiones y errores.
Aplicación Tiempo de respuesta, errores y disponibilidad.
Contenedores Estado, consumo de recursos y reinicios.

Algunas herramientas básicas de Linux son:

# Procesos y consumo de recursos
top

# Memoria
free -h

# Espacio en disco
df -h

# Tiempo de actividad del sistema
uptime

# Estado del servicio Apache
systemctl status apache2

Estas herramientas permiten realizar comprobaciones manuales, aunque no proporcionan por sí solas una plataforma centralizada de monitorización.

9.8. Herramientas de análisis y centralización

Cuando existen varios servidores, revisar los archivos de forma manual resulta poco eficiente. Por ello pueden utilizarse herramientas que recojan, almacenen, busquen y representen los registros de manera centralizada.

GoAccess

Analizador de logs web que permite obtener estadísticas sobre visitas, recursos solicitados, códigos HTTP, agentes de usuario y otras métricas. Puede utilizarse desde terminal o generar informes HTML.

Grafana

Plataforma para visualizar métricas y otras fuentes de datos mediante paneles. Se utiliza habitualmente junto con sistemas de recopilación y almacenamiento de métricas o logs.

Prometheus

Sistema de monitorización orientado a métricas temporales, consultas y alertas. Puede recoger métricas de servicios y sistemas mediante exportadores.

Elastic Stack

Conjunto de herramientas que permite recopilar, indexar, buscar, analizar y visualizar grandes volúmenes de datos, incluidos registros de servidores web.

Conocimiento clave

Estas herramientas tienen finalidades relacionadas, pero no idénticas:

  • GoAccess está especializado en analizar registros web.
  • Prometheus se centra en métricas.
  • Grafana permite visualizar diferentes fuentes de datos.
  • Elastic Stack ofrece capacidades de indexación y búsqueda de registros a gran escala.

9.9. Ejemplo de análisis con GoAccess

En Debian podemos instalar GoAccess mediante APT si está disponible en los repositorios configurados: 

apt update
apt install goaccess
Ejemplo 6

Generar un informe HTML de Apache

Para analizar el registro de accesos de Apache y generar un informe HTML: 

goaccess /var/log/apache2/access.log \
    --log-format=COMBINED \
    -o informe.html

El archivo informe.html contiene un informe estadístico de las peticiones registradas.

Importante

El informe debe publicarse o consultarse de forma segura, ya que los registros pueden contener información sobre usuarios, direcciones IP, rutas y parámetros de las peticiones.

No conviene dejar el informe accesible públicamente sin protección.

9.10. Big Data y toma de decisiones

Cuando una infraestructura recibe millones de peticiones, los registros pueden alcanzar volúmenes muy grandes.

Las técnicas de análisis de datos permiten identificar patrones y tendencias que resultarían difíciles de observar manualmente.

Por ejemplo:

  • Detectar un aumento repentino de errores HTTP.
  • Identificar las rutas que generan más tráfico.
  • Comparar el número de peticiones entre periodos.
  • Localizar horas de mayor demanda.
  • Detectar patrones de solicitudes anómalas.
  • Estimar necesidades futuras de recursos.

El análisis debe tener en cuenta la calidad de los datos, los posibles falsos positivos, la privacidad y el contexto de la infraestructura.

Una frecuencia elevada de peticiones desde una misma IP, por ejemplo, no demuestra por sí sola que exista un ataque.
