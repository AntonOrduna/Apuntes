UD4. Integridade e consistencia dos datos

Nesta última parte da unidade estudaranse os mecanismos que permiten garantir que a información almacenada nunha base de datos sexa correcta, coherente e fiable. Tamén se aplicarán os coñecementos adquiridos sobre manipulación de datos, subconsultas, guións SQL, transaccións e concorrencia mediante dous procesos prácticos integradores.

1. Integridade e consistencia da información

1.1. Concepto de integridade dos datos

A integridade dos datos é o conxunto de regras e mecanismos que permiten garantir que a información almacenada nunha base de datos cumpre determinadas condicións de validez e coherencia.

Unha base de datos non debe limitarse a almacenar información. Tamén debe impedir, na medida do posible, que se introduzan datos incorrectos, duplicados ou incompatibles coas relacións existentes.

Por exemplo, nunha base de datos dunha academia:

  • Non pode haber dous alumnos co mesmo identificador.
  • Un alumno non pode estar asociado a un curso que non existe.
  • O nome dun alumno non pode quedar baleiro se é obrigatorio.
  • A idade dun alumno debe cumprir as regras definidas pola aplicación.
  • Non debería permitirse unha matrícula cunha nota fóra do intervalo establecido.

1.2. Tipos de integridade

Podemos distinguir diferentes tipos de integridade:

Tipo Descrición Exemplo
Integridade de entidade Identifica de forma única cada rexistro. Un alumno ten un identificador único.
Integridade referencial Garantía de coherencia entre táboas relacionadas. Unha matrícula debe referenciar un alumno existente.
Integridade de dominio Limita os valores que pode almacenar un campo. Unha nota debe estar entre 0 e 10.
Integridade de negocio Aplica regras específicas do funcionamento da organización. Un alumno non pode matricularse dúas veces no mesmo módulo.

2. Restricións de integridade en MariaDB

MariaDB permite definir restricións nas táboas para controlar os datos que se poden inserir ou modificar. Estas restricións compróbanse durante as operacións de modificación e permiten evitar moitos erros antes de que os datos queden almacenados.

2.1. PRIMARY KEY

A restrición PRIMARY KEY identifica de maneira única cada rexistro dunha táboa. Non permite valores duplicados nin valores NULL.

Unha táboa só pode ter unha clave primaria, aínda que esta pode estar formada por un único campo ou por varios campos. 

CREATE TABLE alumnos (
    id INT AUTO_INCREMENT,
    nombre VARCHAR(100) NOT NULL,
    edad INT,
    PRIMARY KEY (id)
) ENGINE=InnoDB;

Neste exemplo, o campo id identifica de forma única cada alumno. Ao utilizar AUTO_INCREMENT, MariaDB xera automaticamente os identificadores.

Clave primaria composta

Unha clave primaria tamén pode estar formada por varios campos. É habitual nas táboas que representan relacións N:M. 

CREATE TABLE matriculas (
    alumno_id INT,
    modulo_id INT,
    fecha DATE NOT NULL,
    PRIMARY KEY (alumno_id, modulo_id)
) ENGINE=InnoDB;

A combinación de alumno_id e modulo_id debe ser única. Así, un mesmo alumno non pode ter dúas matrículas para o mesmo módulo.

2.2. FOREIGN KEY

A restrición FOREIGN KEY establece unha relación entre dúas táboas e garante a integridade referencial.

Unha clave foránea debe referenciar unha clave primaria ou unha clave única compatible da táboa relacionada. 

CREATE TABLE cursos (
    id INT AUTO_INCREMENT,
    nombre VARCHAR(50) NOT NULL,
    PRIMARY KEY (id)
) ENGINE=InnoDB;

CREATE TABLE alumnos (
    id INT AUTO_INCREMENT,
    nombre VARCHAR(100) NOT NULL,
    curso_id INT,
    PRIMARY KEY (id),
    CONSTRAINT fk_alumnos_cursos
        FOREIGN KEY (curso_id)
        REFERENCES cursos(id)
) ENGINE=InnoDB;

A clave foránea curso_id impide asociar un alumno a un curso que non exista na táboa cursos.

Se se intenta inserir un alumno cun identificador de curso inexistente, MariaDB xerará un erro de integridade referencial. 

INSERT INTO alumnos (nombre, curso_id)
VALUES ('Ana García', 999);

Se non existe o curso 999, a inserción será rexeitada.

Accións ON DELETE e ON UPDATE

As claves foráneas permiten definir que sucede cando se elimina ou modifica o rexistro referenciado. 

CREATE TABLE alumnos (
    id INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    curso_id INT,
    CONSTRAINT fk_alumnos_cursos
        FOREIGN KEY (curso_id)
        REFERENCES cursos(id)
        ON DELETE SET NULL
        ON UPDATE CASCADE
) ENGINE=InnoDB;
Opción Comportamento
RESTRICT Impide eliminar ou modificar o rexistro referenciado se existen referencias.
CASCADE Propaga a eliminación ou modificación aos rexistros relacionados.
SET NULL Establece a NULL os campos da clave foránea.
NO ACTION En InnoDB ten un comportamento equivalente a RESTRICT.
Para utilizar ON DELETE SET NULL, o campo da clave foránea debe permitir valores NULL. Se o campo está definido como NOT NULL, esta acción non é compatible.

2.3. UNIQUE

A restrición UNIQUE impide que dous rexistros teñan o mesmo valor nun campo ou na combinación de campos definida.

É útil para garantir que determinados datos non se repitan, como un correo electrónico, un nome de usuario ou un código identificador. 

CREATE TABLE usuarios (
    id INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    email VARCHAR(150) NOT NULL,
    CONSTRAINT uk_usuarios_email UNIQUE (email)
) ENGINE=InnoDB;

Se se intenta inserir outro usuario co mesmo correo electrónico, a operación será rexeitada. 

INSERT INTO usuarios (nombre, email)
VALUES ('Ana', 'ana@exemplo.com');

INSERT INTO usuarios (nombre, email)
VALUES ('Luis', 'ana@exemplo.com');

A segunda inserción producirá un erro porque o correo electrónico xa existe.

En MariaDB, unha restrición UNIQUE permite varios valores NULL, xa que NULL non se considera igual a outro NULL nas comprobacións de unicidade.

2.4. NOT NULL

A restrición NOT NULL obriga a que un campo teña sempre un valor. Non permite inserir nin actualizar ese campo con NULL. 

CREATE TABLE profesores (
    id INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    especialidad VARCHAR(100) NOT NULL,
    telefono VARCHAR(20)
) ENGINE=InnoDB;

Neste exemplo, o nome e a especialidade son obrigatorios, mentres que o teléfono é opcional.

Importante: un campo NOT NULL non impide almacenar unha cadea baleira ('') nin un valor formado por espazos. Se tamén se deben impedir eses valores, será necesaria unha validación adicional.

2.5. CHECK

A restrición CHECK permite definir unha condición que deben cumprir os valores almacenados nun campo ou nunha combinación de campos. 

CREATE TABLE matriculas (
    id INT AUTO_INCREMENT PRIMARY KEY,
    alumno_id INT NOT NULL,
    modulo_id INT NOT NULL,
    nota DECIMAL(4,2),
    CONSTRAINT chk_nota
        CHECK (nota IS NULL OR nota BETWEEN 0 AND 10)
) ENGINE=InnoDB;

A condición permite que a nota sexa NULL cando aínda non foi cualificada, pero se contén un valor, este debe estar entre 0 e 10.

Outros exemplos de restricións CHECK:

-- Idade positiva
CHECK (edad > 0)

-- Prezo non negativo
CHECK (precio >= 0)

-- Data de finalización posterior á de inicio
CHECK (fecha_fin >= fecha_inicio)

-- Stock non negativo
CHECK (stock >= 0)

MariaDB aplica as restricións CHECK nas versións modernas. Se a condición non se cumpre, a operación de inserción ou actualización será rexeitada.

2.6. Combinar restricións

Nunha táboa real é habitual utilizar varias restricións simultaneamente. 

CREATE TABLE produtos (
    id INT AUTO_INCREMENT,
    codigo VARCHAR(20) NOT NULL,
    nombre VARCHAR(100) NOT NULL,
    precio DECIMAL(10,2) NOT NULL,
    stock INT NOT NULL DEFAULT 0,

    PRIMARY KEY (id),
    CONSTRAINT uk_produtos_codigo
        UNIQUE (codigo),
    CONSTRAINT chk_produtos_precio
        CHECK (precio >= 0),
    CONSTRAINT chk_produtos_stock
        CHECK (stock >= 0)
) ENGINE=InnoDB;

Esta definición garante que:

  • Cada produto ten un identificador único.
  • O código do produto é obrigatorio e non se pode repetir.
  • O nome e o prezo son obrigatorios.
  • O prezo non pode ser negativo.
  • O stock non pode ser negativo.
  • Se non se indica o stock, utilizarase o valor predeterminado 0.

2.7. Modificar e consultar restricións

As restricións tamén se poden engadir a táboas xa existentes. 

-- Engadir unha restrición UNIQUE
ALTER TABLE usuarios
ADD CONSTRAINT uk_usuarios_email
UNIQUE (email);

-- Engadir unha restrición CHECK
ALTER TABLE produtos
ADD CONSTRAINT chk_produtos_stock
CHECK (stock >= 0);

-- Engadir unha clave foránea
ALTER TABLE alumnos
ADD CONSTRAINT fk_alumnos_cursos
FOREIGN KEY (curso_id)
REFERENCES cursos(id);

Para eliminar unha restrición: 

-- Eliminar unha clave foránea
ALTER TABLE alumnos
DROP FOREIGN KEY fk_alumnos_cursos;

-- Eliminar unha restrición CHECK
ALTER TABLE produtos
DROP CONSTRAINT chk_produtos_stock;

-- Eliminar unha restrición UNIQUE
ALTER TABLE usuarios
DROP INDEX uk_usuarios_email;

Para consultar a definición dunha táboa e as súas restricións: 

SHOW CREATE TABLE alumnos;

SHOW CREATE TABLE produtos;

3. Medidas para garantir a consistencia das operacións

3.1. Concepto de consistencia

A consistencia é a propiedade que garante que as operacións realizadas sobre a base de datos manteñen a información nun estado válido, respectando as regras e restricións definidas.

Unha operación pode modificar varios rexistros ou varias táboas. O obxectivo é evitar que, se algo falla durante o proceso, a base de datos quede nun estado incompleto ou incoherente.

Exemplo: creación dun pedido

Ao crear un pedido nunha tenda en liña é necesario realizar varias operacións:

  1. Crear a cabeceira do pedido.
  2. Inserir as liñas correspondentes aos produtos.
  3. Reducir o stock dos produtos.
  4. Calcular e almacenar o importe total.

Se o pedido se crea pero falla a actualización do stock, a información pode quedar incoherente.

Para evitar esta situación, todas as operacións deben executarse dentro dunha mesma transacción.

3.2. Validación dos datos

Antes de inserir ou modificar información, é necesario comprobar que os datos cumpren as regras establecidas.

As validacións poden realizarse en diferentes niveis:

  • Aplicación: comprobar os datos introducidos polo usuario antes de enviar as operacións SQL.
  • Base de datos: utilizar restricións NOT NULL, UNIQUE, CHECK e claves foráneas.
  • Procedementos almacenados: centralizar determinadas regras de negocio e validacións.

Por exemplo, antes de rexistrar unha venda débese comprobar que existe o produto e que hai unidades suficientes. 

SELECT id, stock, precio
FROM produtos
WHERE id = 1;

A aplicación ou o procedemento debe comprobar o resultado antes de continuar coa operación.

3.3. Utilización de transaccións

As transaccións permiten agrupar varias operacións nunha única unidade de traballo. Se todas as operacións se executan correctamente, confírmanse mediante COMMIT. Se se produce un erro, poden desfacer­se mediante ROLLBACK. 

START TRANSACTION;

INSERT INTO pedidos (cliente_id, fecha, total)
VALUES (1, CURRENT_DATE(), 100.00);

INSERT INTO detalle_pedido
    (pedido_id, producto_id, cantidad, precio)
VALUES
    (LAST_INSERT_ID(), 1, 2, 50.00);

UPDATE produtos
SET stock = stock - 2
WHERE id = 1
  AND stock >= 2;

COMMIT;

O exemplo ilustra a agrupación das operacións, pero unha implementación correcta debe comprobar que a actualización do stock afectou exactamente unha fila e que as insercións se realizaron correctamente. Se algunha operación falla, débese executar ROLLBACK.

3.4. Integridade referencial

As claves foráneas garanten que as relacións entre táboas se manteñan coherentes.

Por exemplo, unha liña de pedido debe referenciar un pedido existente e un produto existente. 

CREATE TABLE detalle_pedido (
    id INT AUTO_INCREMENT PRIMARY KEY,
    pedido_id INT NOT NULL,
    producto_id INT NOT NULL,
    cantidad INT NOT NULL,
    precio DECIMAL(10,2) NOT NULL,

    CONSTRAINT fk_detalle_pedido
        FOREIGN KEY (pedido_id)
        REFERENCES pedidos(id),

    CONSTRAINT fk_detalle_producto
        FOREIGN KEY (producto_id)
        REFERENCES produtos(id),

    CONSTRAINT chk_detalle_cantidad
        CHECK (cantidad > 0),

    CONSTRAINT chk_detalle_precio
        CHECK (precio >= 0)
) ENGINE=InnoDB;

Desta maneira, non será posible crear unha liña de pedido asociada a un pedido ou produto inexistente.

3.5. Control de erros

Un proceso de modificación debe prever que poden producirse erros durante a súa execución. Entre os máis habituais están:

  • Violación dunha clave primaria ou restrición UNIQUE.
  • Inserción dunha clave foránea que non existe.
  • Incumprimento dunha restrición CHECK.
  • Valores obrigatorios que non se proporcionan.
  • Bloqueos e deadlocks.
  • Erros de conexión ou interrupcións durante a operación.

Un procedemento almacenado pode utilizar un xestor de erros para desfacer a transacción cando se produce unha excepción. 

DELIMITER //

CREATE PROCEDURE crear_operacion()
BEGIN
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        RESIGNAL;
    END;

    START TRANSACTION;

    -- Operacións de modificación
    INSERT INTO produtos (codigo, nombre, precio, stock)
    VALUES ('P001', 'Teclado', 25.00, 10);

    -- Confirmar se todo foi correcto
    COMMIT;
END //

DELIMITER ;

O controlador EXIT HANDLER FOR SQLEXCEPTION captura os erros SQL que se produzan no bloque, executa ROLLBACK e transmite novamente o erro mediante RESIGNAL.

Desta maneira, a aplicación que invoque o procedemento tamén pode recibir o erro e actuar en consecuencia.

Boa práctica: as operacións que forman parte dun mesmo proceso lóxico deben executarse nunha transacción. Ademais, deben existir validacións para comprobar que se modificaron os rexistros esperados antes de confirmar os cambios.

4. Práctica integradora: manipulación de datos

4.1. Obxectivo

Desenvolver un proceso de xestión de pedidos que implique varias táboas relacionadas, inserción e modificación de datos, subconsultas, guións SQL e utilización de transaccións.

A práctica permitirá aplicar os coñecementos adquiridos sobre DML, integridade referencial, subconsultas, procedementos almacenados e control de erros.

4.2. Deseño da base de datos

Crear unha base de datos denominada tenda que permita xestionar clientes, produtos, pedidos e liñas de pedido.

A estrutura deberá incluír as seguintes táboas:

Táboa Información almacenada Relacións
clientes Identificador, nome, correo electrónico e cidade. Un cliente pode realizar varios pedidos.
produtos Identificador, código, nome, prezo e stock. Un produto pode aparecer en varias liñas de pedido.
pedidos Identificador, cliente, data e estado. Pertence a un cliente e contén varias liñas.
detalle_pedido Pedido, produto, cantidade e prezo aplicado. Relaciona pedidos e produtos.

As táboas deben utilizar InnoDB e incorporar as claves primarias, claves foráneas e restricións necesarias para garantir a integridade dos datos.

4.3. Inserción inicial de datos

Preparar un conxunto inicial de datos que permita realizar as operacións posteriores:

  • Un mínimo de cinco clientes.
  • Un mínimo de oito produtos con prezos e stocks diferentes.
  • Un mínimo de tres pedidos.
  • Varias liñas de pedido para cada pedido.

As insercións deben realizarse respectando a orde das relacións: primeiro os rexistros das táboas independentes e despois os das táboas que conteñen claves foráneas.

4.4. Operacións de manipulación de datos

Preparar un ficheiro SQL que conteña diferentes operacións de modificación da información.

  • Inserir novos clientes e produtos.
  • Actualizar os prezos dunha categoría ou grupo de produtos.
  • Modificar o stock dos produtos.
  • Eliminar rexistros que cumpran determinadas condicións.
  • Inserir novos pedidos e as súas correspondentes liñas.
  • Actualizar o estado dos pedidos.

4.5. Operacións con subconsultas

Incorporar operacións de modificación que utilicen subconsultas. Como mínimo, deberán incluírse os seguintes casos:

  • Inserir nunha táboa os clientes que cumpran unha determinada condición utilizando INSERT ... SELECT.
  • Actualizar o prezo dos produtos cuxo stock sexa inferior á media do stock almacenado.
  • Eliminar ou actualizar rexistros utilizando EXISTS ou NOT EXISTS.
  • Consultar os produtos que nunca apareceron nun pedido.
  • Modificar os datos dun pedido en función da información almacenada nas súas liñas.

4.6. Elaboración dun procedemento almacenado

Crear un procedemento almacenado denominado realizar_pedido que permita rexistrar un pedido e as súas liñas.

O procedemento debe:

  1. Recibir o identificador do cliente.
  2. Comprobar que o cliente existe.
  3. Iniciar unha transacción.
  4. Crear a cabeceira do pedido.
  5. Inserir as liñas correspondentes.
  6. Comprobar que hai stock suficiente para cada produto.
  7. Actualizar o stock dos produtos.
  8. Calcular o importe total do pedido.
  9. Confirmar a transacción se todas as operacións son correctas.
  10. Executar ROLLBACK se se produce algún erro.

O procedemento debe utilizar parámetros de entrada e, se resulta necesario, parámetros de saída para devolver o identificador do pedido creado ou o seu importe total.

4.7. Control da consistencia

O proceso debe garantir que non se producen pedidos con produtos inexistentes, cantidades negativas ou stocks insuficientes.

Deben comprobarse os resultados das operacións de actualización mediante ROW_COUNT() cando sexa necesario. Tamén se debe garantir que un erro nunha das operacións desfaga todos os cambios realizados durante a transacción.

4.8. Comprobación dos resultados

Ao finalizar, realizar consultas que permitan comprobar:

  • Os pedidos realizados por cada cliente.
  • As liñas e os produtos de cada pedido.
  • O importe total dos pedidos.
  • O stock restante de cada produto.
  • Os produtos que non se venderon.
  • Que non existen referencias a rexistros inexistentes.

5. Práctica integradora: concorrencia e consistencia

5.1. Obxectivo

Analizar o comportamento dunha base de datos cando varias conexións executan operacións simultáneas sobre os mesmos rexistros. A práctica permitirá comprobar os efectos dos bloqueos, os niveis de illamento, as transaccións e os conflitos de concorrencia.

5.2. Preparación do entorno

Utilizarase a base de datos tenda creada na práctica anterior. É necesario dispoñer de dúas conexións independentes desde MySQL Workbench.

Antes de comezar, comprobar que as táboas utilizan InnoDB: 

SHOW TABLE STATUS
FROM tenda;

Tamén se debe consultar o nivel de illamento configurado: 

SELECT @@SESSION.tx_isolation;

5.3. Simulación de actualizacións concorrentes

Seleccionar un produto con stock suficiente e executar actualizacións desde dúas conexións diferentes.

A primeira conexión iniciará unha transacción e modificará o stock dun produto sen confirmar os cambios. 

START TRANSACTION;

UPDATE produtos
SET stock = stock - 2
WHERE id = 1;

A segunda conexión intentará modificar o mesmo rexistro. Observarase se a operación queda bloqueada ata que a primeira transacción confirme ou desfaga os cambios.

5.4. Análise dos niveis de illamento

Repetir unha mesma secuencia de lecturas desde dúas conexións utilizando os seguintes niveis:

  • READ UNCOMMITTED
  • READ COMMITTED
  • REPEATABLE READ
  • SERIALIZABLE

Para cada nivel, analizar se unha transacción pode observar os cambios doutra e se as consultas repetidas devolven os mesmos resultados.

5.5. Utilización de bloqueos explícitos

Executar unha lectura con bloqueo exclusivo: 

START TRANSACTION;

SELECT *
FROM produtos
WHERE id = 1
FOR UPDATE;

Desde a segunda conexión, intentar modificar o mesmo produto. Observar o comportamento e comprobar que a operación espera a liberación do bloqueo.

Repetir a proba utilizando un bloqueo compartido: 

START TRANSACTION;

SELECT *
FROM produtos
WHERE id = 1
LOCK IN SHARE MODE;

Analizar a diferenza entre ambos os tipos de bloqueo e o efecto que teñen sobre as operacións concorrentes.

5.6. Detección e resolución de deadlocks

Provocar un bloqueo mutuo utilizando dúas transaccións que modifiquen dous produtos en diferente orde.

Identificar:

  • Que rexistros bloquea cada transacción.
  • En que momento se produce a espera.
  • Que erro devolve MariaDB.
  • Que transacción foi cancelada.
  • Que cambios quedaron confirmados.

Consultar o estado de InnoDB: 

SHOW ENGINE INNODB STATUS;

5.7. Resolución dos conflitos

Modificar a secuencia de operacións para reducir a posibilidade de deadlocks:

  • Acceder aos produtos sempre na mesma orde.
  • Reducir a duración das transaccións.
  • Utilizar consultas que seleccionen só os rexistros necesarios.
  • Utilizar índices adecuados.
  • Controlar os erros e repetir as operacións canceladas cando proceda.

5.8. Verificación da consistencia final

Ao rematar as probas, realizar unha revisión dos datos almacenados. Comprobar que:

  • Non existen stocks negativos.
  • Non hai pedidos asociados a clientes inexistentes.
  • Non hai liñas de pedido asociadas a produtos inexistentes.
  • Os importes dos pedidos coinciden coas súas liñas.
  • As transaccións canceladas non deixaron cambios parciais.
  • As operacións confirmadas mantiveron a integridade dos datos.

6. Conclusión da unidade didáctica

A manipulación de datos nun sistema xestor de bases de datos non consiste unicamente en executar sentenzas de inserción, modificación e eliminación. É necesario garantir que esas operacións se realizan de maneira controlada e que a información resultante mantén a súa integridade e consistencia.

Para conseguir este obxectivo, MariaDB ofrece diferentes mecanismos:

  • Restricións de integridade: controlan os valores e as relacións entre táboas.
  • Transaccións: agrupan operacións e permiten confirmar ou desfacer cambios.
  • Bloqueos: coordinan o acceso simultáneo de varias transaccións.
  • Niveis de illamento: controlan a visibilidade dos cambios entre transaccións.
  • Control de erros: permite reaccionar ante operacións incorrectas e evitar estados inconsistentes.

A combinación destes mecanismos permite construír procesos de manipulación de datos fiables, mesmo cando varias aplicacións ou usuarios traballan simultaneamente sobre a mesma base de datos.
