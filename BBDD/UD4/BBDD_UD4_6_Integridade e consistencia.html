UD4. Integridade e consistencia dos datos

Unha base de datos debe almacenar información correcta, coherente e relacionada adecuadamente. Non abonda con que os datos se poidan inserir, consultar ou modificar: tamén é necesario garantir que cumpran unhas regras que eviten valores incorrectos, referencias inexistentes e operacións que deixen a información nun estado inconsistente.

MariaDB proporciona diferentes mecanismos para protexer a integridade da información. Entre eles destacan as restricións das táboas, as claves primarias e alleas, as validacións de datos e o uso de transaccións.

1. Integridade e consistencia da información

1.1. Que é a integridade dos datos?

A integridade dos datos é a propiedade que garante que a información almacenada nunha base de datos sexa correcta, válida e cumpra as regras definidas para o sistema.

Estas regras permiten evitar situacións como:

  • Rexistros sen identificador ou con identificadores duplicados.
  • Campos obrigatorios que conteñen valores nulos.
  • Valores repetidos en columnas que deberían ser únicas.
  • Rexistros que fan referencia a elementos que non existen.
  • Valores fóra dos límites permitidos.
  • Operacións que deixan varias táboas con información contraditoria.

1.2. Que é a consistencia?

A consistencia é a propiedade pola que unha base de datos mantén todas as regras de integridade antes e despois de cada operación ou transacción correctamente executada.

Unha operación pode modificar varios rexistros ou táboas. Se todos os cambios se realizan correctamente, a base de datos debe quedar nun estado válido. Se se produce un erro, os cambios parciais non deben deixar información incoherente.

Exemplo: matrículas dunha academia

Nunha academia existen alumnos e cursos. Cada matrícula relaciona un alumno cun curso.

O sistema debe garantir que:

  • Cada alumno teña un identificador único.
  • Cada curso teña un identificador único.
  • Unha matrícula sempre corresponda a un alumno existente.
  • Unha matrícula sempre corresponda a un curso existente.
  • Un alumno non poida matricularse dúas veces no mesmo curso.

Estas condicións permiten manter a información relacionada de maneira coherente.

1.3. Tipos de integridade

Tipo Descrición Exemplo
Integridade de entidade Garantir que cada rexistro poida identificarse de forma única. Clave primaria nunha táboa de alumnos.
Integridade referencial Garantir que as relacións entre táboas sexan válidas. Unha matrícula debe referenciar un alumno existente.
Integridade de dominio Garantir que os valores cumpran as condicións definidas para cada campo. Unha nota debe estar entre 0 e 10.
Integridade definida pola aplicación Garantir regras específicas do funcionamento do sistema. Non permitir unha matrícula nun curso completo.

2. Restricións de integridade en MariaDB

2.1. Concepto de restrición

Unha restrición (constraint) é unha regra que se define sobre unha táboa ou unha columna para limitar os valores que se poden almacenar.

MariaDB comproba estas regras cando se executan operacións como INSERT ou UPDATE. Se unha operación viola unha restrición, o sistema xera un erro e non permite realizar esa modificación.

As principais restricións utilizadas son:

  • PRIMARY KEY: identifica de forma única cada rexistro.
  • FOREIGN KEY: garante a integridade das relacións entre táboas.
  • UNIQUE: impide que se repitan determinados valores.
  • NOT NULL: obriga a proporcionar un valor.
  • CHECK: verifica que se cumpra unha condición.

2.2. PRIMARY KEY

A restrición PRIMARY KEY define a clave primaria dunha táboa. A súa finalidade é identificar de forma única cada rexistro.

As súas características principais son:

  • Non pode haber dous rexistros coa mesma clave primaria.
  • Os valores non poden ser NULL.
  • Unha táboa só pode ter unha clave primaria.
  • A clave pode estar formada por unha ou varias columnas.

Exemplo dunha clave primaria simple:

CREATE TABLE alumnos (
    id INT PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    apelidos VARCHAR(150)
) ENGINE=InnoDB;

Neste caso, a columna id identifica unicamente cada alumno.

Exemplo dunha clave primaria composta:

CREATE TABLE matriculas (
    alumno_id INT,
    curso_id INT,
    data_matricula DATE,
    PRIMARY KEY (alumno_id, curso_id)
) ENGINE=InnoDB;

A combinación de alumno_id e curso_id identifica cada matrícula. Así, un mesmo alumno non poderá ter dúas matrículas para o mesmo curso.

2.3. FOREIGN KEY

A restrición FOREIGN KEY, ou clave allea, establece unha relación entre dúas táboas. Permite garantir que os valores dunha columna dunha táboa correspondan a rexistros existentes noutra táboa.

A táboa que contén a clave allea denomínase táboa dependente ou táboa filla. A táboa á que se fai referencia denomínase táboa principal ou táboa pai.

Exemplo: alumnos e cursos

Cada alumno está asociado a un curso. A columna curso_id da táboa alumnos referencia a columna id da táboa cursos. 

CREATE TABLE cursos (
    id INT PRIMARY KEY,
    nome VARCHAR(100) NOT NULL
) ENGINE=InnoDB;

CREATE TABLE alumnos (
    id INT PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    curso_id INT,
    CONSTRAINT fk_alumnos_cursos
        FOREIGN KEY (curso_id)
        REFERENCES cursos(id)
) ENGINE=InnoDB;

A clave allea impide inserir un alumno cun identificador de curso que non exista na táboa cursos. Se curso_id admite NULL, tamén se poderá inserir un alumno sen curso asociado.

Políticas de eliminación e actualización

As claves alleas permiten definir que debe suceder cando se elimina ou modifica un rexistro da táboa principal.

Opción Comportamento
RESTRICT Impide eliminar ou modificar o rexistro principal se existen rexistros dependentes.
CASCADE Propaga a eliminación ou modificación aos rexistros dependentes.
SET NULL Establece a NULL a clave allea dos rexistros dependentes.
NO ACTION En InnoDB ten un comportamento equivalente a RESTRICT.

Exemplo utilizando ON DELETE e ON UPDATE:

CREATE TABLE alumnos (
    id INT PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    curso_id INT,

    CONSTRAINT fk_alumnos_cursos
        FOREIGN KEY (curso_id)
        REFERENCES cursos(id)
        ON DELETE SET NULL
        ON UPDATE CASCADE
) ENGINE=InnoDB;

Neste exemplo:

  • Se se elimina un curso, os alumnos asociados conservan o rexistro, pero a súa columna curso_id pasa a ser NULL.
  • Se cambia o identificador dun curso, o novo valor propágase aos alumnos relacionados.
Para utilizar ON DELETE SET NULL, a columna que contén a clave allea debe admitir valores NULL. Ademais, CASCADE debe utilizarse con coidado, xa que unha eliminación pode propagarse a moitos rexistros relacionados.

2.4. UNIQUE

A restrición UNIQUE garante que os valores dunha columna ou combinación de columnas non se repitan.

A diferenza de PRIMARY KEY, unha táboa pode ter varias restricións UNIQUE e, dependendo da definición, estas columnas poden admitir valores NULL. 

CREATE TABLE usuarios (
    id INT PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    correo VARCHAR(150) UNIQUE
) ENGINE=InnoDB;

Neste exemplo non se permite que dous usuarios teñan o mesmo correo electrónico. Se a columna admite NULL, MariaDB pode aceptar varios valores nulos nun índice UNIQUE.

Tamén se pode definir unha restrición única sobre varias columnas: 

CREATE TABLE matriculas (
    alumno_id INT,
    curso_id INT,
    convocatoria VARCHAR(20),

    CONSTRAINT uq_matricula
        UNIQUE (alumno_id, curso_id, convocatoria)
) ENGINE=InnoDB;

A combinación das tres columnas non poderá repetirse.

2.5. NOT NULL

A restrición NOT NULL obriga a que unha columna conteña un valor. Non se permite almacenar NULL nesa columna. 

CREATE TABLE cursos (
    id INT PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    horas INT NOT NULL
) ENGINE=InnoDB;

Non se poderá inserir un curso sen nome ou sen número de horas.

É importante distinguir entre un valor nulo e unha cadea baleira:

  • NULL representa a ausencia dun valor.
  • '' é unha cadea de texto baleira.
  • 0 é un valor numérico igual a cero.

Unha columna NOT NULL pode conter unha cadea baleira se o seu tipo de dato o permite. Se tamén se quere impedir ese valor, será necesaria unha validación adicional.

2.6. CHECK

A restrición CHECK permite establecer unha condición que deben cumprir os valores dunha fila.

É especialmente útil para validar límites numéricos, estados permitidos ou condicións entre varias columnas. 

CREATE TABLE asignaturas (
    id INT PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    horas INT NOT NULL,

    CONSTRAINT chk_horas
        CHECK (horas > 0)
) ENGINE=InnoDB;

Neste exemplo non se permite inserir unha asignatura cun número de horas igual ou inferior a cero.

Outro exemplo con valores limitados:

CREATE TABLE avaliacions (
    id INT PRIMARY KEY,
    alumno_id INT NOT NULL,
    nota DECIMAL(4,2) NOT NULL,

    CONSTRAINT chk_nota
        CHECK (nota >= 0 AND nota <= 10)
) ENGINE=InnoDB;

A nota debe estar comprendida entre 0 e 10.

Tamén se poden definir condicións entre columnas: 

CREATE TABLE ofertas (
    id INT PRIMARY KEY,
    prezo DECIMAL(10,2) NOT NULL,
    desconto DECIMAL(10,2) NOT NULL,

    CONSTRAINT chk_desconto
        CHECK (
            desconto >= 0
            AND desconto <= prezo
        )
) ENGINE=InnoDB;
Nas versións modernas de MariaDB, as restricións CHECK son aplicadas polo servidor. Se a condición non se cumpre, a operación de inserción ou actualización xera un erro.

3. Definición e modificación das restricións

3.1. Definir restricións ao crear unha táboa

As restricións poden declararse directamente dentro da sentenza CREATE TABLE. 

CREATE TABLE alumnos (
    id INT AUTO_INCREMENT,
    nome VARCHAR(100) NOT NULL,
    correo VARCHAR(150),
    idade INT NOT NULL,
    curso_id INT,

    CONSTRAINT pk_alumnos
        PRIMARY KEY (id),

    CONSTRAINT uq_alumnos_correo
        UNIQUE (correo),

    CONSTRAINT chk_alumnos_idade
        CHECK (idade >= 16),

    CONSTRAINT fk_alumnos_cursos
        FOREIGN KEY (curso_id)
        REFERENCES cursos(id)
        ON DELETE SET NULL
) ENGINE=InnoDB;

Neste exemplo defínense varias restricións:

  • Un identificador único para cada alumno.
  • Un correo electrónico que non se pode repetir.
  • Unha idade mínima de 16 anos.
  • Unha relación coa táboa de cursos.
  • A posibilidade de deixar o alumno sen curso se este se elimina.

3.2. Engadir restricións a unha táboa existente

A sentenza ALTER TABLE permite engadir novas restricións sen ter que eliminar e crear de novo a táboa.

Engadir unha restrición UNIQUE:

ALTER TABLE alumnos
ADD CONSTRAINT uq_alumnos_correo
UNIQUE (correo);

Engadir unha clave allea:

ALTER TABLE alumnos
ADD CONSTRAINT fk_alumnos_cursos
FOREIGN KEY (curso_id)
REFERENCES cursos(id);

Engadir unha restrición CHECK:

ALTER TABLE alumnos
ADD CONSTRAINT chk_alumnos_idade
CHECK (idade >= 16);

Modificar unha columna para que non admita NULL:

ALTER TABLE alumnos
MODIFY nome VARCHAR(100) NOT NULL;

Antes de engadir unha restrición a unha táboa con datos, é necesario comprobar que os rexistros existentes cumpren a nova condición. Se hai valores duplicados, nulos ou referencias incorrectas, a operación pode fallar.

3.3. Eliminar restricións

As restricións tamén se poden eliminar cando xa non son necesarias.

Eliminar unha clave allea:

ALTER TABLE alumnos
DROP FOREIGN KEY fk_alumnos_cursos;

Eliminar unha restrición UNIQUE:

ALTER TABLE alumnos
DROP INDEX uq_alumnos_correo;

Eliminar unha restrición CHECK:

ALTER TABLE alumnos
DROP CONSTRAINT chk_alumnos_idade;

Para eliminar unha restrición NOT NULL, débese modificar a definición da columna: 

ALTER TABLE alumnos
MODIFY nome VARCHAR(100) NULL;

3.4. Consultar as restricións dunha táboa

A estrutura dunha táboa pode consultarse mediante: 

DESCRIBE alumnos;

SHOW CREATE TABLE alumnos;

SHOW CREATE TABLE mostra a definición completa da táboa, incluíndo as claves primarias, claves alleas, índices e restricións.

Tamén se poden consultar as restricións mediante as vistas do esquema information_schema: 

SELECT
    CONSTRAINT_NAME,
    CONSTRAINT_TYPE,
    TABLE_NAME
FROM information_schema.TABLE_CONSTRAINTS
WHERE TABLE_SCHEMA = 'academia';

4. Validación dos datos

4.1. Que é a validación?

A validación consiste en comprobar que os datos recibidos ou xerados por unha aplicación cumpren as condicións necesarias antes de almacenalos na base de datos.

A validación pode realizarse en diferentes niveis:

  • Na interface da aplicación, antes de enviar os datos.
  • Na lóxica de negocio, antes de executar as sentenzas SQL.
  • Na propia base de datos, mediante restricións e tipos de datos.

É recomendable combinar estes mecanismos. A validación na aplicación mellora a experiencia do usuario, pero as restricións da base de datos son necesarias para protexer a información fronte a calquera cliente que acceda ao servidor.

4.2. Validación mediante tipos de datos

A elección correcta dos tipos de datos é unha primeira medida de protección.

Tipo Uso habitual Exemplo
INT Identificadores e cantidades enteiras. Número de alumnos.
DECIMAL Importes e valores decimais exactos. Prezo dun produto.
DATE Datas. Data de matrícula.
VARCHAR Texto de lonxitude variable. Nome e correo electrónico.
BOOLEAN Valores lóxicos. Activo ou inactivo.

4.3. Validación mediante restricións

As restricións permiten delegar no propio servidor a comprobación das regras básicas. 

CREATE TABLE produtos (
    id INT PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    prezo DECIMAL(10,2) NOT NULL,
    stock INT NOT NULL DEFAULT 0,
    activo BOOLEAN NOT NULL DEFAULT TRUE,

    CONSTRAINT chk_prezo
        CHECK (prezo >= 0),

    CONSTRAINT chk_stock
        CHECK (stock >= 0)
) ENGINE=InnoDB;

A táboa impide almacenar produtos sen nome, con prezos negativos ou con cantidades de stock inferiores a cero.

4.4. Validación de operacións complexas

Hai regras que non se poden expresar facilmente mediante unha restrición dunha soa táboa.

Por exemplo:

  • Non permitir unha matrícula se o curso está completo.
  • Non permitir unha retirada de diñeiro superior ao saldo dispoñible.
  • Non permitir que un pedido supere un determinado límite de crédito.
  • Non permitir que un produto se venda se está marcado como inactivo.

Estas condicións deben comprobarse mediante lóxica de aplicación, procedementos almacenados ou transaccións que consulten e modifiquen os datos de forma segura.

5. Transaccións para garantir a consistencia

5.1. A relación entre transaccións e consistencia

Unha transacción agrupa varias operacións SQL nunha única unidade de traballo. Todas as operacións deben completarse correctamente ou, se se produce un erro, os cambios pendentes deben desfacer­se.

Isto permite evitar que unha operación composta deixe a base de datos nun estado parcial.

5.2. Exemplo: transferencia entre contas

Supoñamos que se necesita transferir 100 euros dunha conta a outra. A operación implica dúas actualizacións:

  1. Restar 100 euros da conta de orixe.
  2. Engadir 100 euros á conta de destino.

Se só se executa a primeira actualización e a segunda falla, a información quedaría inconsistente. 

START TRANSACTION;

UPDATE contas
SET saldo = saldo - 100
WHERE id = 1
  AND saldo >= 100;

-- Comprobar que se modificou exactamente unha fila.

UPDATE contas
SET saldo = saldo + 100
WHERE id = 2;

-- Comprobar que se modificou exactamente unha fila.

COMMIT;

Antes de confirmar a transacción é imprescindible verificar que ambas as actualizacións afectaron exactamente un rexistro. Se algunha non se realizou correctamente, débese executar ROLLBACK.

Non se debe executar COMMIT automaticamente despois das dúas sentenzas sen comprobar os resultados. Unha transferencia segura require validar a existencia das contas, o saldo dispoñible e o número de filas modificadas. Para evitar conflitos con outras operacións simultáneas, tamén se deben bloquear os rexistros necesarios mediante SELECT ... FOR UPDATE.

5.3. Propiedades ACID

As transaccións de InnoDB baséanse nas propiedades ACID, que permiten garantir a fiabilidade das operacións.

Propiedade Significado Finalidade
Atomicidade As operacións execútanse como unha unidade. Evitar cambios parciais.
Consistencia A transacción debe manter as regras de integridade. Evitar estados inválidos.
Illamento As transaccións concorrentes non deben interferir incorrectamente. Controlar os accesos simultáneos.
Durabilidade Os cambios confirmados deben persistir. Conservar os datos despois dun fallo.

6. Integridade referencial nas operacións

6.1. Por que é importante?

A integridade referencial garante que as relacións entre táboas non conteñan referencias incorrectas.

Por exemplo, unha matrícula non pode facer referencia a un alumno que non exista. Do mesmo xeito, non se debería eliminar un curso se existen matrículas que dependen del, salvo que se teña definido unha política que controle esa eliminación.

6.2. Exemplo de integridade referencial

CREATE TABLE cursos (
    id INT PRIMARY KEY,
    nome VARCHAR(100) NOT NULL
) ENGINE=InnoDB;

CREATE TABLE alumnos (
    id INT PRIMARY KEY,
    nome VARCHAR(100) NOT NULL
) ENGINE=InnoDB;

CREATE TABLE matriculas (
    id INT PRIMARY KEY AUTO_INCREMENT,
    alumno_id INT NOT NULL,
    curso_id INT NOT NULL,
    data_matricula DATE NOT NULL,

    CONSTRAINT fk_matriculas_alumnos
        FOREIGN KEY (alumno_id)
        REFERENCES alumnos(id)
        ON DELETE RESTRICT,

    CONSTRAINT fk_matriculas_cursos
        FOREIGN KEY (curso_id)
        REFERENCES cursos(id)
        ON DELETE RESTRICT,

    CONSTRAINT uq_alumno_curso
        UNIQUE (alumno_id, curso_id)
) ENGINE=InnoDB;

Esta estrutura garante que:

  • Non se pode crear unha matrícula sen un alumno existente.
  • Non se pode crear unha matrícula sen un curso existente.
  • Non se pode eliminar un alumno que teña matrículas relacionadas.
  • Non se pode eliminar un curso que teña matrículas relacionadas.
  • Un alumno non pode matricularse dúas veces no mesmo curso.

6.3. Orde correcta das operacións

As claves alleas condicionan a orde na que se deben realizar as operacións de inserción e eliminación.

Para inserir datos:

  1. Inserir primeiro os rexistros das táboas principais.
  2. Inserir despois os rexistros das táboas dependentes.

Para eliminar datos:

  1. Eliminar primeiro os rexistros das táboas dependentes.
  2. Eliminar despois os rexistros das táboas principais.

Se se utilizan políticas como ON DELETE CASCADE, o propio motor pode propagar a eliminación aos rexistros dependentes.

7. Control de erros nas operacións SQL

7.1. Por que é necesario controlar os erros?

Durante a execución dunha operación poden producirse erros por diferentes motivos:

  • Violación dunha clave primaria ou dunha restrición UNIQUE.
  • Inserción dun valor NULL nunha columna NOT NULL.
  • Incumprimento dunha condición CHECK.
  • Referencia a un rexistro inexistente mediante unha clave allea.
  • Actualización ou eliminación de datos que non cumpren as regras de integridade referencial.
  • Erros de conexión, permisos ou bloqueo entre transaccións.

Se unha operación forma parte dunha transacción, é importante detectar o erro e decidir se se pode continuar ou se é necesario desfacer todos os cambios.

7.2. Exemplo de erro por clave allea

Supoñamos que a táboa cursos contén os identificadores 1 e 2. A seguinte inserción tenta crear un alumno asociado ao curso 99: 

INSERT INTO alumnos (id, nome, curso_id)
VALUES (10, 'Ana', 99);

MariaDB rexeitará a operación porque non existe ningún curso co identificador 99.

7.3. Exemplo de erro por CHECK

INSERT INTO avaliacions (id, alumno_id, nota)
VALUES (1, 10, 15);

Se a táboa ten definida a restrición CHECK (nota >= 0 AND nota <= 10), a operación será rexeitada porque a nota supera o máximo permitido.

7.4. Control de erros en procedementos almacenados

MariaDB permite definir controladores de erros mediante DECLARE ... HANDLER dentro de procedementos almacenados.

Estes controladores permiten executar accións específicas cando se produce unha excepción SQL. 

DELIMITER //

CREATE PROCEDURE inserir_alumno(
    IN p_id INT,
    IN p_nome VARCHAR(100),
    IN p_curso_id INT
)
BEGIN
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        RESIGNAL;
    END;

    START TRANSACTION;

    INSERT INTO alumnos (id, nome, curso_id)
    VALUES (p_id, p_nome, p_curso_id);

    COMMIT;
END //

DELIMITER ;

Neste procedemento:

  • Iníciase unha transacción antes de inserir o alumno.
  • Se se produce un erro SQL, actívase o controlador.
  • ROLLBACK desfai os cambios pendentes.
  • RESIGNAL volve lanzar o erro para que a aplicación que chamou ao procedemento poida coñecelo.
  • Se non hai erros, execútase COMMIT.
Nota: os controladores de erros permiten centralizar a xestión das excepcións, pero non substitúen a validación previa dos datos nin a definición das restricións na base de datos.

7.5. Control de filas afectadas

Unha operación SQL pode executarse sen producir un erro e, con todo, non modificar ningún rexistro porque non se cumpra a condición indicada no WHERE.

Por iso, en operacións importantes é recomendable comprobar cantas filas se modificaron mediante ROW_COUNT(). 

UPDATE contas
SET saldo = saldo - 100
WHERE id = 1
  AND saldo >= 100;

SELECT ROW_COUNT();

Se o resultado é 1, modificouse un rexistro. Se é 0, non se modificou ningún, posiblemente porque a conta non existe ou non ten saldo suficiente.

Se se esperan exactamente unha ou varias filas, a aplicación debe comparar o resultado co número esperado e actuar en consecuencia.

8. Boas prácticas para garantir a integridade e consistencia

Para deseñar unha base de datos fiable é recomendable aplicar as seguintes medidas:

  1. Definir correctamente os tipos de datos. Utilizar tipos adecuados ao contido que se vai almacenar.
  2. Establecer claves primarias. Todas as táboas deben ter un mecanismo fiable de identificación.
  3. Definir claves alleas. As relacións entre táboas deben estar protexidas mediante integridade referencial.
  4. Utilizar restricións UNIQUE e NOT NULL. Impedir duplicidades e valores obrigatorios ausentes.
  5. Definir restricións CHECK. Validar límites e condicións que deban cumprirse sempre.
  6. Utilizar transaccións. Agrupar as operacións que forman parte dunha mesma unidade de traballo.
  7. Controlar os erros. Ante un erro, desfacer os cambios pendentes cando sexa necesario.
  8. Comprobar as filas afectadas. Verificar que as modificacións se realizaron sobre os rexistros esperados.
  9. Controlar a concorrencia. Utilizar bloqueos e niveis de illamento adecuados cando varias transaccións acceden aos mesmos datos.
  10. Evitar desactivar as restricións sen necesidade. Non utilizar mecanismos que permitan introducir datos inconsistentes como solución habitual a un problema.

9. Resumo de restricións

Restrición Finalidade Exemplo
PRIMARY KEY Identificar un rexistro de forma única. PRIMARY KEY (id)
FOREIGN KEY Garantir relacións válidas entre táboas. FOREIGN KEY (curso_id) REFERENCES cursos(id)
UNIQUE Impedir valores duplicados. UNIQUE (correo)
NOT NULL Obrigar a proporcionar un valor. nome VARCHAR(100) NOT NULL

10. Guión de comprobación

Antes de dar por rematado o deseño dunha base de datos ou unha operación de modificación, convén comprobar os seguintes aspectos:

  • As táboas teñen claves primarias correctamente definidas.
  • As relacións entre táboas utilizan claves alleas.
  • Os campos obrigatorios están definidos como NOT NULL.
  • Os campos que non deben repetir valores teñen restricións UNIQUE.
  • Os valores numéricos e os estados cumpren as condicións CHECK necesarias.
  • As políticas ON DELETE e ON UPDATE responden ás necesidades do sistema.
  • As operacións que modifican varias táboas utilizan transaccións.
  • Os erros provocan a cancelación dos cambios cando corresponde.
  • Compróbase o número de filas afectadas nas operacións críticas.
  • As operacións concorrentes non poden deixar información inconsistente.
